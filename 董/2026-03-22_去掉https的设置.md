## 议题 1: 移除 Payload 加密 (明文传输模式实现与开关配置)

### 背景与需求
最初，Happy Coder 的架构使用 `libsodium` (通过 `TweetNaCl`) 对 CLI/Daemon 与后端服务器之间的所有 API 请求和 WebSocket 消息进行端到端的 Payload 加密。
为了方便本地开发、网络抓包调试以及在安全内网环境中的集成，我们需要提供一个可配置的开关，允许禁用这种加密，改为使用明文（Plaintext）进行数据传输。

### 实现细节

我们通过引入全局环境变量 `ENABLE_PLAINTEXT_MODE=true` 作为控制开关来实现这一需求。

1. **后端服务器 (`packages/happy-server/src/api/crypto.ts`)**:
   - 我们修改了 `decryptRequest` 和 `encryptResponse` 两个核心辅助函数。
   - 当 `process.env.ENABLE_PLAINTEXT_MODE === 'true'` 时，函数会检查传入的 Payload 字符串是否以 `PLAINTEXT:` 作为前缀。如果是，则直接截取前缀后的内容作为 JSON 字符串进行解析。
   - 对于向外发送的响应，不再执行 NaCl 加密和 Base64 编码，而是直接返回格式为 `PLAINTEXT:<json_字符串>` 的内容。
   - *结果*: 后端现在可以根据环境变量和 Payload 前缀，动态、兼容地处理加密和明文两种数据。

2. **CLI/Daemon 客户端 (`packages/happy-cli/src/api/encryption.ts`)**:
   - 同样更新了 `encrypt` 和 `decrypt` 函数。
   - 当检测到 `process.env.ENABLE_PLAINTEXT_MODE === 'true'` 时，`encrypt` 函数会直接将对象序列化为 JSON 并拼接 `PLAINTEXT:` 前缀，完全跳过 `libsodium` 的加密过程。
   - 相对地，`decrypt` 会检查传入的字符串（可能经过 Base64 解码）是否以 `PLAINTEXT:` 开头。如果是，则剥离前缀并解析 JSON。
   - *注意*: 为了兼容现有的传输层（某些模块依然会对内容进行 Base64 包装），`decrypt` 的逻辑被设计得足够健壮，它会先尝试 Base64 解码，然后再检查是否存在 `PLAINTEXT:` 签名。

### 遇到的问题与解决方案

*   **问题 1: 混合状态导致解析崩溃**: 在过渡期间或配置不一致时（例如服务端开启了明文，但 CLI 没有，或反之），直接将加密数据当作 JSON 解析会导致严重的语法错误（如 `SyntaxError: Unexpected token 'P', "PLAINTEXT:"... is not valid JSON`）。
    *   *解决方案*: 我们引入了明确的 `PLAINTEXT:` 前缀协议。客户端和服务端在尝试将内容作为明文解析或作为 NaCl 密文解密之前，都会**强制检查这个确切的签名**。这种防御性编程防止了在收到不匹配的 Payload 类型时发生致命崩溃。
*   **问题 2: 外层遗留的 Base64 包装**: 即使底层的 `encrypt` 生成了 `PLAINTEXT:` 字符串，上层的 API 方法（如 `apiSession.ts` 或 WebSocket 发送器）依然在盲目地将结果通过 `encodeBase64()` 进行二次包装。
    *   *解决方案*: 我们调整了 `decrypt` 函数，让它首先尝试读取原始字节并进行 Base64 解码。如果在解码后的内容中发现了 `PLAINTEXT:` 前缀，我们就将其视为明文处理。这使得我们能够在不破坏外层 Base64 传输协议的前提下，成功绕过实际的密码学运算。

### 如何切换回 HTTPS / 加密传输模式？

该功能已经完全满足了“通过开关进行设置”的要求。**默认情况下，系统是安全的加密模式。**

如果你需要关闭明文模式，**恢复使用原始的 `libsodium` 加密传输**，只需执行以下操作：

1. **对于后端服务器**: 
   - 停止当前的 Server 进程。
   - 在启动 Server 时，移除或将环境变量设置为 false：`ENABLE_PLAINTEXT_MODE=false`。
   - 例如，修改你的启动脚本 `./01-start-server.sh`，去掉该环境变量的注入，或者直接运行：`ENABLE_PLAINTEXT_MODE=false bash ./01-start-server.sh`。
2. **对于 Daemon/CLI 客户端**:
   - 停止当前的 Daemon 进程 (可以运行 `happy daemon stop` 或在终端中 `Ctrl+C`)。
   - 同样在启动时移除该环境变量，或者明确设为 false。
   - 例如：`ENABLE_PLAINTEXT_MODE=false yarn workspace happy-coder cli daemon start-sync`。
3. **对于 Web 前端 (如果有相关配置)**:
   - 确保 `EXPO_PUBLIC_ENABLE_PLAINTEXT_MODE` 环境变量也被移除或设为 `false`，并重新启动 Web 服务。

**机制说明**: 当 `ENABLE_PLAINTEXT_MODE` 变量不存在或不为 `'true'` 时，代码会自动回退，继续调用 `TweetNaCl` 库进行高强度的加解密，无需修改任何业务代码。

## 议题 2: Daemon "已读不回" (收到 WebSocket 更新但未拉取消息)

### 故障现象
在 Web UI 发送消息后，消息成功到达后端，后端也向 Daemon 推送了 WebSocket 的 `update` (具体为 `new-message`) 事件。Daemon 的日志显示已收到该事件，但随后并未向服务器拉取具体的文本内容，导致 AI 助手表现为“卡死”或“忽略”了用户的指令。

### 根本原因分析
该问题是由消息同步队列的状态机死锁与 API 层的异常处理不当共同导致的。

1.  **队列状态死锁 (`InvalidateSync`)**:
    *   在 `packages/happy-cli/src/utils/sync.ts` 中，`InvalidateSync` 类使用了一个 `_invalidated` 布尔标志位来防止同步命令被并发执行。
    *   如果传入的 `_command()` (即 `fetchMessages`) 抛出了未被捕获的异常，`_doSync` 方法就会在重置 `this._invalidated = false` 之前崩溃退出。
    *   一旦 `_invalidated` 永久卡在 `true` 的状态，后续所有由新 WebSocket 消息触发的 `invalidate()` 调用都会直接 `return`，什么也不做。

2.  **异常穿透 (`fetchMessages`)**:
    *   在 `packages/happy-cli/src/api/apiSession.ts` 中，`fetchMessages` 方法原本的设计是：当 `axios.get` 遇到网络问题（如 HTTP 500 或请求超时）时，直接抛出错误 (`throw err;`)。
    *   这本意是想让外层的 `backoff` 重试机制来接管失败。然而，这个异常直接穿透了调用栈，导致了上述 `InvalidateSync` 的致命死锁。

3.  **编译遗漏 (隐蔽的坑)**:
    *   当 Daemon 派生(spawn)一个新的 Session 时（例如响应 Web UI 的请求），它使用的是 `child_process.spawn` 去执行**已编译好**的 `dist/index.mjs` 文件，而**不是**原始的 TypeScript 源码文件。
    *   因此，仅仅修改 `.ts` 源文件（如 `apiSession.ts` 或 `sync.ts`）并重启 Daemon 进程（Daemon 本身用 `tsx` 跑源码）是无效的。派生出的子进程依然会运行 `dist` 目录下带有 Bug 的旧代码，直到你手动执行 `yarn build`。

### 解决方案与最佳实践

1.  **阻止核心任务的异常穿透**:
    *   修改 `fetchMessages`，优雅地“吞下”异常，而不是抛出它们。当发生网络错误时，只需使用 `break` 跳出当前的拉取循环即可。
    *   这使得当前的同步周期能够干净地结束，从而重置队列状态（`_invalidated = false`），保证**下一次** `invalidate()` 触发时可以正常重试拉取。
    *   *代码修改:* 在 `apiSession.ts` 中，将 `fetchMessages` `catch` 块里的 `throw err;` 替换为了 `break;`。

2.  **健壮的状态机设计**:
    *   确保 `InvalidateSync` 中的 `_doSync` 方法在执行 `this._command()` 时被严密的 `try...catch` 块包裹。
    *   这保证了无论传入的命令内部发生了什么灾难性错误，状态机最终都能执行到清理阶段，恢复可用状态。

3.  **至关重要的开发工作流**:
    *   在修改了 daemon 或 API 通信相关的逻辑后，**务必在 `packages/happy-cli` 目录下运行 `yarn build`**。
    *   Daemon 严重依赖编译后的产物 `dist/index.mjs` 来启动 Worker 进程。没有全新的构建，源码的修改永远无法在子进程中生效。
