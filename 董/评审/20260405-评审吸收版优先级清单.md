# 20260405 评审吸收版优先级清单

**创建时间：** 2026-04-05  
**目的：** 吸收《gstack 评审意见》与 5 个专项报告的有效结论，并按当前仓库真实状态重排 HelloVibe 的后续优先级

---

## 1. 使用原则

- 保留评审文档的长处：专题化拆解、执行步骤、验收标准、风险说明
- 修正已过时的判断：以当前仓库代码、最近验证结果、最新工作结论为准
- 不把“已接入”误判为“已闭环”
- 不把“已完成部分”误判为“尚未开始”

---

## 2. 当前吸收后的核心判断

### 2.1 评审文档最值得直接吸收的部分

1. **tgz 安装闭环** 应继续保留为对外交付主线
2. **包内容瘦身** 应继续保留为 P0，且问题根因已足够明确
3. **付费墙/订阅** 必须单独列为商业化主线，不能再隐含在品牌或设置页工作里
4. **仓库统一** 适合作为协作治理专项继续推进
5. **每个 blocker 需要独立验收标准**，不能只用“感觉差不多了”判断完成

### 2.2 需要修正的判断

1. **tgz 安装闭环不是“待开始”**
   - 当前已不只是 `npm pack --dry-run`
   - 已进入真实安装、真实执行、真实 daemon、真实 hosted/tmux 的验证层级
   - 后续重点应转为“产品化交付边界收口”，而不是再次把它当成纯概念验证

2. **品牌统一不是“尚未实施”**
   - `happy-app` 的 Expo 名称、Bundle ID、图标配置已切到 HelloVibe
   - 移动端页面层文案、Logo、设置页、导航页等已完成多轮替换
   - 当前剩余问题主要是原生 build、桌面端、文档术语、CLI/npm 命名等残留

3. **付费墙不是“已完成”，而是“基础设施已接入，商业闭环未完成”**
   - 后端 quota、plans、subscription current 已具备基础能力
   - RevenueCat 集成与 paywall 展示入口已具备
   - 支付订单、真实支付通道、学生认证、完整转化路径仍未闭环

4. **核心链路稳定性应单列，不应散落在文档外**
   - `/handoff/mac` 正式入口真回归
   - happy-server 的 quota / Prisma / build / tests 历史问题
   - 移动端 permission 通过后状态刷新可靠性
   - 这些都应作为独立收口事项，而不是零散插入其他主线

---

## 3. 吸收后的优先级重排

### P0：必须先收口的主线

#### P0-1. 执行端对外交付边界收口

**目标：** 把“已经能真实安装和运行”推进到“能稳定作为产品交付”

**保留评审结论：**
- tgz 安装闭环仍然是对外交付底座
- 必须保留验收标准和真实安装验证

**按当前状态修正后的重点：**
- 不再重复证明“是否能安装”
- 转而确认：
  - 安装包内容是否干净
  - 安装步骤是否最小化
  - 安装后 `auth` / `daemon` / hosted / tmux 是否可稳定复现
  - 交付说明是否能支持外部用户完成首次使用

**完成标准：**
- 有真实 tarball 安装闭环记录
- 有最小安装步骤
- 有稳定复现的安装后运行验证项
- 不依赖本地研发环境特例

#### P0-2. npm 包内容瘦身

**目标：** 解决 tarball 体积偏大和内容边界不清的问题

**直接吸收评审结论：**
- `tools/archives/` 是当前大体积的主要根因
- 应明确白名单/黑名单，而不是继续模糊打包

**当前判断：**
- 这条结论命中很准，仍是 P0
- 但方案选型要优先考虑最短闭环，不必一开始就追求最理想终态

**推荐执行顺序：**
1. 先确认 `files` 与 `.npmignore` 的最小正确边界
2. 先把明显不该进包的内容排出去
3. 再决定采用运行时下载还是平台分发策略

**完成标准：**
- tarball 体积明显下降
- 包中不再混入无必要二进制档案
- 安装后 CLI 核心链路仍可用

#### P0-3. 核心链路稳定性收口

**目标：** 避免“功能实际上已完成，但前端/正式入口看起来像卡住或失效”

**纳入范围：**
- `/handoff/mac` 正式入口真回归
- happy-server quota / Prisma / build / tests 旧问题拆线收口
- 移动端 permission 通过后的 session/messages 同步刷新可靠性

**当前判断：**
- 这条主线虽然不在原始 5 大 blocker 中，但现在应进入 P0
- 它直接影响用户是否感知为“产品能不能用”

**完成标准：**
- handoff/mac 正式入口无回归
- 服务端关键链路不再把历史问题混成一锅
- 移动端在权限处理后能及时刷新最新进度与结果

#### P0-4. 商业化闭环最小版本

**目标：** 明确“能展示 paywall”与“能完成商业转化”之间的缺口，并收最小闭环

**保留评审结论：**
- 付费功能不能遗漏
- 需要单列支付、学生认证、付费墙 UI、实验能力

**按当前状态修正后的重点：**
- 当前不是从 0 开始
- 已有 quota 基础、订阅计划、RevenueCat 集成、paywall 展示入口
- 当前真正的 blocker 是：
  - 支付订单与真实支付通道
  - 升级后权益生效链路
  - 取消/降级链路

**完成标准：**
- 至少一条真实升级路径可跑通
- 升级后权益与配额正确更新
- 用量超限后的引导与购买链路一致

### P1：基线立住后立刻推进

#### P1-1. 品牌统一残留收口

**目标：** 从“代码层大半完成”推进到“用户感知层基本统一”

**当前剩余范围：**
- 原生 dev build 名称/图标刷新
- Tauri 图标与桌面端实际显示确认
- 文档与开发说明中的旧品牌术语
- CLI 包名、命令名、仓库展示名残留

**判断：**
- 这不再是“要不要开始”的问题
- 而是“把剩余残留按层次逐批收干净”

#### P1-2. 仓库统一与单一事实来源

**目标：** 建立 HelloVibe 唯一主仓库与协作基线

**保留评审结论：**
- 多 remote 并存确实增加协作复杂度
- 仓库统一是品牌化和协作治理的最后一公里

**按当前状态修正后的重点：**
- 仓库统一要服务于协作，不要为了形式抢在 P0 链路前面
- 应在“已有可协作基线”的前提下推进

**完成标准：**
- 主仓库唯一
- remote 关系清晰
- 新任务、新文档、新代码只围绕单一仓库推进

### P2：P0/P1 稳定后再做

#### P2-1. CLI/npm 全量品牌迁移

- npm 包名迁移
- CLI 命令名迁移
- 仓库展示、外链、发布流程统一

#### P2-2. 商业化增强项

- 学生认证完整流程
- 定价页视觉优化
- A/B 测试与埋点体系
- 邮件营销与转化运营工具

#### P2-3. 多 Agent 常态化并行放大

- 在单仓库、单 owner、低冲突边界稳定后再扩并行面

## 4. 当前统一认知

### 4.1 可以明确认为已进入“后半段”的事项

- 移动端品牌替换
- app.config.js 品牌配置
- RevenueCat/paywall 基础接入
- tgz 安装形态第一阶段验证

### 4.2 仍然不能误判为“完成”的事项

- npm 对外交付版本的最终收口
- tarball 瘦身
- 真实支付闭环
- handoff/mac 正式入口最终回归确认
- 仓库唯一化切换

### 4.3 当前最容易产生误判的点

1. 把“文档已清楚”当成“工程已完成”
2. 把“功能入口已存在”当成“端到端闭环已成立”
3. 把“品牌文案已替换”当成“原生壳、桌面端、CLI、仓库都已统一”
4. 把“某个现象能绕过”当成“正式链路已稳定”

---

## 5. 建议采用的执行顺序

1. 先收执行端对外交付边界
2. 同步做包内容瘦身
3. 并行收核心链路稳定性
4. 补最小商业化闭环
5. 再做品牌残留与仓库统一
6. 最后做命令名、包名、实验体系等扩展性工作

---

## 6. 一句话结论

**评审文档最值得保留的是“把 blocker 写成执行手册”的方法；吸收之后的正确优先级应是：先交付、再稳定、再变现、再统一残留，而不是重新从“是否开始”讨论。**
