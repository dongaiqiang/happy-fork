# 20260405 需求清单：迁到 HelloVibe 仓库推进方案

## 1. 文档目的

这份文档只解决一件事：

把当前工程从“历史上主要在 SoEasyWork 语境下推进”，切换为“后续正式以 HelloVibe 仓库为唯一主承接仓库”的迁移路径定清楚。

这里要回答的问题包括：

1. 当前是否还需要先向 SoEasyWork 提交一版  
2. 什么时候开始把 HelloVibe 作为唯一主仓库  
3. 迁移时哪些内容应该先收口，哪些内容应后置  
4. 如何避免出现两个仓库长期并行写入、状态分叉  
5. 后续 Trae、Claude Code、Codex 等 Agent 应该围绕哪个仓库协作

关联文档：

1. 上层总纲文档见《20260405 需求清单：HelloVibe 基线建设与总体推进方案》  
2. 多 Agent 协作规则见《20260405 需求清单：多 Agent 协作制度清单》  
3. 执行端安装与品牌专项见《20260401 需求清单：执行端 NPM 安装与品牌化命名》

使用方式建议：

1. 先用本文档确定仓库迁移策略和提交顺序  
2. 再回到总纲文档判断整体优先级  
3. 进入具体实现时，再按专项文档和协作文档执行

---

## 2. 当前背景

当前工程已经处于一个比较特殊的中间状态：

1. 本地已经积累了较多有效改动  
2. HelloVibe 远端仓库已经建立，但还没有完全成为唯一主仓库  
3. SoEasyWork 仍然承载着一部分历史上下文和当前代码状态认知  
4. 后续工作又明确希望逐步统一到 HelloVibe 品牌和 HelloVibe 仓库之下  
5. 多 Agent 协作也要求必须尽快收敛到单一真相源

这意味着当前最忌讳的不是“迁得慢一点”，而是：

1. 两个仓库长期双写  
2. 一个仓库存历史，一个仓库存未来，但两边都持续改  
3. 迁移之前没有先定义什么该进、什么不该进  
4. 迁移之后仍然继续把临时成果散落在旧仓库

---

## 3. 当前总判断

当前更合理的策略不是直接跳过 SoEasyWork，也不是继续长期依赖 SoEasyWork。

建议判断如下：

1. 可以先在 SoEasyWork 做一次“阶段性收口提交”，但只限已经稳定、值得保留的成果  
2. 不建议后续长期继续把新工作主线放在 SoEasyWork  
3. HelloVibe 应尽快切换为后续唯一主仓库  
4. 一旦 HelloVibe 进入正式承接状态，后续新增工作应全部围绕 HelloVibe 展开

更直白地说：

1. SoEasyWork 更适合做“历史阶段的收口”  
2. HelloVibe 才适合做“后续阶段的主承接”  
3. 关键不是是否两边都提交过，而是不能长期两边都继续当主仓库

---

## 4. 迁移目标

这次迁移建议同时实现四个目标。

### 4.1 历史阶段有一个可回看的收口点

目标：

1. 让 SoEasyWork 至少保留一版对当前阶段有意义的收口记录  
2. 避免后续回看时，发现旧阶段成果全都只停留在本地

### 4.2 HelloVibe 成为唯一正式主仓库

目标：

1. 让 HelloVibe 成为后续所有代码、文档、协作的唯一正式承接点  
2. 让新任务不再在多个仓库之间漂移

### 4.3 提交边界清楚

目标：

1. 迁移前先明确哪些改动属于“可提交成果”  
2. 不把临时实验、混杂状态、未验证内容一起推上去

### 4.4 多 Agent 协作收敛到单一真相源

目标：

1. 后续 Trae、Claude Code、Codex 都围绕 HelloVibe 协作  
2. 避免不同 Agent 基于不同仓库上下文工作

---

## 5. 推荐策略

建议采用“先收口旧仓库，再切主仓库，随后单仓持续推进”的策略。

具体来说：

1. 先判断 SoEasyWork 当前是否存在必须保留的一批稳定成果  
2. 如果有，就做一次收口型提交  
3. 完成后，尽快把 HelloVibe 切换为唯一正式主仓库  
4. 从切换点开始，后续新增工作只进入 HelloVibe  
5. SoEasyWork 从此不再承担未来主线开发

这个策略的优点是：

1. 历史有交代  
2. 未来有归口  
3. 迁移边界清楚  
4. 不会让两个仓库长期打架

---

## 6. 三阶段推进方式

### 6.1 第一阶段：SoEasyWork 收口阶段

这一阶段的目标不是继续大开发，而是判断 SoEasyWork 是否需要留下一个阶段性版本。

建议只纳入以下内容：

1. 已经验证通过的主链路修复  
2. 已形成明确结论的需求文档  
3. 后续迁移时仍然需要回看的关键工程调整  
4. 不会因为后面品牌统一而马上被整体推翻的基础性成果

不建议纳入以下内容：

1. 临时实验代码  
2. 未验证的半成品  
3. 明显属于 HelloVibe 新阶段才适合承接的混杂改动  
4. 品牌统一的一次性大规模改名  
5. 仍在快速变化中的高冲突收口区

阶段结论应满足：

1. SoEasyWork 有一个“截至当前阶段”的清晰收口点  
2. 但不再继续作为未来主线开发仓库

### 6.2 第二阶段：HelloVibe 基线导入阶段

这一阶段的目标是把 HelloVibe 从“已经创建的远端仓库”，切换成“正式承接后续工作的主仓库”。

重点包括：

1. 确定第一批进入 HelloVibe 的基线内容  
2. 优先导入协作基线、稳定文档、关键工程基础调整  
3. 不追求一次性把所有混杂改动全量搬过去  
4. 明确后续主分支、集成分支、任务分支策略  
5. 让多人和多 Agent 后续都以 HelloVibe 为真相源

阶段结论应满足：

1. HelloVibe 已经可以承接后续开发  
2. 后续任务可以直接从 HelloVibe 开始分发和推进

### 6.3 第三阶段：HelloVibe 唯一主线阶段

这一阶段开始后，规则应明确为：

1. 所有新增功能  
2. 所有新增修复  
3. 所有新增文档  
4. 所有多 Agent 任务分发  
5. 所有后续集成与提交

全部以 HelloVibe 为唯一正式主线。

SoEasyWork 在这一阶段只保留历史参考价值，不再承担未来推进职责。

---

## 7. 第一批进入 HelloVibe 的建议内容

建议优先进入 HelloVibe 的，不是“改得最多的内容”，而是“最适合做协作基线的内容”。

优先建议包括：

1. 已经稳定的需求清单与协作文档  
2. 已经验证通过的主链路修复  
3. 后续所有工作都要依赖的基础工程调整  
4. 当前阶段已经明确、不会被很快推翻的结论型改动

不建议第一批就进入 HelloVibe 的内容包括：

1. 大范围品牌改名  
2. 大规模目录搬迁  
3. 尚未收口的 tgz 包体积瘦身细节  
4. 仍在快速变动的 server 高冲突区域  
5. 仅用于临时验证的实验性脚本或临时文件

核心原则是：

1. 先把 HelloVibe 立成“可协作基线”  
2. 再在这个基线上继续做专项推进  
3. 不在第一次导入时追求全量完成

---

## 8. 是否需要先提交 SoEasyWork

针对“是否先提交一版到现在的 SoEasyWork 仓库，再全量迁到 HelloVibe”的问题，当前建议是：

### 8.1 可以先提交，但前提要满足

满足以下条件时，可以先在 SoEasyWork 做一次收口提交：

1. 这批内容已经稳定  
2. 这批内容确实代表当前阶段成果  
3. 这批内容后续仍值得回看  
4. 提交后不会导致你又继续把 SoEasyWork 当主仓库使用

### 8.2 不满足条件时，不必勉强提交

如果当前 SoEasyWork 中的大部分改动仍然混杂、未验证、边界不清，那么也不必为了“形式完整”强行提交一版。

此时更合理的是：

1. 先在本地收口  
2. 直接按主题整理后导入 HelloVibe  
3. 把 HelloVibe 作为真正开始持续管理的起点

### 8.3 关键不是先后，而是切换点必须明确

无论是否先在 SoEasyWork 留一次收口版本，最重要的是：

1. 必须明确一个切换点  
2. 切换点之后，新增工作只进 HelloVibe  
3. 不允许以后继续长期双仓并行主写

---

## 9. 对多 Agent 协作的影响

仓库迁移一旦不清楚，多 Agent 协作很快就会失控。

因此迁移完成后应明确：

1. Trae 的主调度上下文以 HelloVibe 为准  
2. Claude Code 的方案、review、只读分析也以 HelloVibe 为准  
3. Codex 后续专项接入同样以 HelloVibe 为准  
4. handoff、任务分发、评审、集成全部围绕 HelloVibe 展开

不建议出现以下情况：

1. Trae 基于 HelloVibe 工作  
2. Claude Code 却仍基于 SoEasyWork 给建议  
3. 最后不同 Agent 看的不是同一份代码现实

这会让协作制度形同虚设。

---

## 10. 风险点

迁到 HelloVibe 仓库时，重点要防以下风险。

### 10.1 双仓长期并行

风险：

1. 两边都有新提交  
2. 后续很难判断哪个才是真正主线  
3. 文档和代码上下文会逐渐分叉

### 10.2 第一次导入过大

风险：

1. 把未验证内容一起导入  
2. 让 HelloVibe 初始基线就变得混乱  
3. 后续 review 和分批提交难度暴增

### 10.3 迁移后继续频繁改迁移边界

风险：

1. 今天说迁，明天又回旧仓库补  
2. 后续所有人都不知道当前应该基于哪个仓库工作

### 10.4 品牌统一与仓库迁移混成一次大动作

风险：

1. 迁移本来是版本管理问题  
2. 品牌统一本来是命名与产品表达问题  
3. 两者混成一次提交后，风险和回滚成本都会明显上升

---

## 11. 推荐执行顺序

建议按以下顺序推进：

1. 先盘点当前改动，区分“可收口成果”和“暂不导入内容”  
2. 判断 SoEasyWork 是否需要留一个阶段性收口提交  
3. 明确 HelloVibe 第一批导入内容  
4. 把 HelloVibe 设为后续唯一主仓库  
5. 后续新增工作全部在 HelloVibe 中推进  
6. 再按专项主线继续做 npm、品牌、多 Agent 等后续事项

这个顺序的核心不是求快，而是求切换点清楚。

---

## 12. 可直接执行的操作清单

为了把迁移从“讨论结论”变成“可执行动作”，建议按下面四步直接推进。

### 12.1 盘点

1. 盘点当前本地改动，按模块列出文件清单  
2. 标记每项改动的状态：已验证、待验证、临时实验  
3. 标记每项改动的属性：稳定成果、阶段性成果、暂不导入  
4. 同时标记高冲突区域，避免迁移阶段多人同时改动

产出物：

1. 一份可收口改动清单  
2. 一份暂不导入清单

### 12.2 筛选

1. 从盘点结果中筛出 SoEasyWork 是否需要阶段性收口提交的内容  
2. 保留可回看且已稳定的成果  
3. 剔除未验证、混杂、临时性改动  
4. 明确哪些内容将作为 HelloVibe 第一批导入内容

产出物：

1. SoEasyWork 收口提交候选清单  
2. HelloVibe 第一批导入候选清单

### 12.3 第一批导入

1. 先完成 SoEasyWork 阶段收口提交（如果前一步判断为需要）  
2. 按“协作基线优先”原则导入 HelloVibe 第一批内容  
3. 第一批只导入稳定基础，不追求全量  
4. 导入后立即检查文档和协作规则是否都已指向 HelloVibe

产出物：

1. HelloVibe 第一批基线版本  
2. 对应的导入边界说明

### 12.4 切换点声明

1. 明确一个切换时间点或切换提交点  
2. 从该点开始，新增代码和文档只进入 HelloVibe  
3. SoEasyWork 停止承担未来主线开发，仅保留历史参考  
4. 在协作文档中同步这条规则，避免多 Agent 继续双仓并行

产出物：

1. 一条明确的“切换后规则”  
2. 一份团队可复用的迁移执行基线

---

## 13. 结论

当前最合理的路线是：

1. SoEasyWork 可以视情况做一次阶段性收口  
2. 但不应继续承担后续主线开发  
3. HelloVibe 应尽快切换为唯一正式主仓库  
4. 切换后所有新增工作都从 HelloVibe 展开  
5. 仓库迁移、品牌统一、执行端交付、多 Agent 协作应分主线推进，不混成一次大提交

一句话总结：

可以先给 SoEasyWork 一个“历史阶段的收口版本”，但未来必须尽快统一到 HelloVibe，而且一旦切过去，就不要再长期双仓并行主写。
