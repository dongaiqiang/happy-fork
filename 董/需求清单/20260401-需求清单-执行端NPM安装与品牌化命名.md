# 20260401 需求清单：执行端 NPM 安装与品牌化命名

## 1. 文档目的

本需求文档聚焦一个新的交付问题：

- 当前执行端主要按源码仓库方式部署
- 这适合自己研发与联调
- 但不适合在不暴露源码的前提下交付给其他机器或其他人安装

本需求的目标，是把执行端收敛为一种更易交付的安装形态：

1. 支持通过 npm 安装  
2. 支持通过打包产物安装  
3. 支持使用自定义品牌名，而不是固定沿用 `happy-coder / happy`

关联文档：

1. 上层总纲文档见《20260405 需求清单：HelloVibe 基线建设与总体推进方案》  
2. 多 Agent 协作规则见《20260405 需求清单：多 Agent 协作制度清单》  
3. 本文档聚焦执行端安装与品牌命名专项，不承担 HelloVibe 全局推进细节

使用方式建议：

1. 先用总纲文档判断当前整体阶段与优先级  
2. 再用本文档推进执行端安装、打包、命名专项  
3. 涉及多人或多 Agent 分工时，再回到协作制度文档对齐边界

---

## 2. 问题背景

当前整体架构已经逐步清晰：

1. Web 前端部署在阿里云  
2. Server 部署在阿里云  
3. 本地 Mac 或其他机器只承担执行端角色

但执行端当前仍主要依赖：

1. 拉源码仓库  
2. `yarn install`  
3. 本地构建  
4. 再启动 daemon

这会带来几个问题：

1. 若交付给其他机器，不想直接暴露源码  
2. 若交付给外部用户，希望安装方式更接近普通 CLI 工具  
3. 若后续要品牌化，不希望继续直接使用 `happy-coder`、`happy` 这些既有命名  
4. 研发调试版与对外交付版的安装形态目前还没有明确区分

因此需要把“执行端 npm 化 + 品牌化命名”单独定义为一个独立需求。

---

## 3. 核心需求

## 3.1 需求描述

后续执行端需要支持以下交付方式：

1. 公开 npm 包安装  
2. 私有 npm 包或私有源安装  
3. `npm pack` 生成的 `.tgz` 安装包交付  
4. 在不暴露源码仓库的前提下完成执行端安装与启动

同时，执行端需要支持后续品牌化命名：

1. npm 包名可改为自定义名称，例如 `hellovibe-coder` 或 `hellovibe-cli`  
2. CLI 命令名也可同步改为自定义名称  
3. 交付时不要求对方继续使用 `happy-coder` 和 `happy`
4. GitHub 仓库归属与对外展示需支持从 `slopus/hellovibe` 切换为 `dongaiqiang/hellovibe`
5. 后续如继续品牌化，执行端安装命令、升级命令、诊断命令也要评估是否统一迁移到 `hellovibe` 体系，而不是长期保留 `happy` / `happy-coder`

## 3.2 用户价值

1. 降低执行端交付门槛  
2. 避免必须把源码仓库发给对方  
3. 支持更标准的 CLI 分发方式  
4. 为后续独立品牌命名预留空间  
5. 让执行端安装更接近常规 SaaS/CLI 产品体验

## 3.3 功能定义

### A. 安装形态

执行端至少应支持三种安装形态：

1. `npm install -g 包名`  
2. `npm install -g ./xxx.tgz`  
3. 在 CI 或本地先产出可安装包，再分发给目标机器

### B. 命名形态

命名需要拆成两个层面定义：

1. npm 包名  
2. 命令行入口名

例如：

1. 包名从 `happy-coder` 改为 `hellovibe-coder`  
2. 命令从 `happy` 改为 `hellovibe`

两者可以同步改，也可以先只改包名、后续再改命令名。

同时新增一条明确约束：

1. 对外仓库展示名优先使用 `dongaiqiang/hellovibe`
2. 若后续要统一 CLI 品牌名，应优先采用全小写命名，例如 `hellovibe`、`hellovibe-cli`、`hellovibe-coder`
3. 不直接把可执行命令设计为带大写的 `HelloVibe`，避免与 npm 包名、终端命令约定冲突

### C. 运行形态

即使改成 npm 安装，执行端仍需保留现有核心能力：

1. 认证  
2. daemon 启动  
3. daemon 状态检查  
4. tmux 托管能力  
5. 与阿里云 Web / Server 配合工作

也就是说，本需求改变的是“交付与安装方式”，不是重写执行端产品能力。

### D. 产品术语与命名梳理

除了 npm 安装形态和品牌名之外，这次还暴露出一个更底层的产品化问题：

1. 当前手机浏览器、原生 App、Mac 执行端三条链路并存  
2. 同一个动作在不同入口里用了不同名字  
3. 一些技术侧术语直接暴露给用户，普通用户很难判断自己现在是在“登录账号”“绑定机器”还是“切换会话”

这会直接带来理解成本：

1. 用户容易把“创建账户”和“终端登录”理解成同一件事  
2. 用户容易把“连接终端”和“Open in Mac”理解成同一件事  
3. 用户容易把“认证、连接、公钥、终端请求”这些技术词当成业务动作，但其实并不知道下一步该点什么

因此后续产品化梳理时，需要把“品牌命名”与“用户术语”一起统一处理，而不是只改 npm 包名或 CLI 命令名。

当前已确认需要重点收口的术语包括：

1. `创建账户`  
2. `使用移动应用登录`  
3. `连接终端`  
4. `接受连接`  
5. `Open in Mac`  
6. `auth login` / `daemon` 相关对外描述

除了术语问题，这轮联调还新增暴露出一个执行体验问题：

1. Mac 端进入远程模式后，终端内容格式偶尔会显得较乱  
2. 用户虽然已经能正常使用，但桌面端展示还不够稳定、整洁  
3. 这类问题不影响链路打通，但会直接影响产品完成度与可交付感受

目标不是把词写得更技术化，而是让普通用户第一次看到就能明白：

1. 这是在新建账号  
2. 这是在恢复旧账号  
3. 这是在把一台 Mac 加入当前账号  
4. 这是在把当前会话切到 Mac 继续

同时也要让用户在切到 Mac 继续工作时，终端界面足够清晰，至少满足：

1. 关键状态提示不互相打架  
2. 正文内容不因为远程模式而明显错行或堆叠  
3. 用户能一眼分清当前是查看态、只读态还是 Mac 控制态

## 4. 产品原则

1. 源码可选：交付执行端时不强制给对方源码仓库  
2. 安装标准化：尽量通过 npm 或 tgz 安装完成  
3. 能力不回退：认证、daemon、tmux、Open in Mac 相关能力保持可用  
4. 命名可演进：先支持包名改造，再考虑命令名与品牌统一  
5. 术语要直白：优先让普通用户看懂，而不是优先沿用内部技术叫法  
6. 桌面展示要稳：Mac 远程模式下终端视图要清晰、整洁、可读  
7. 发布可控：研发内测版与对外交付版应有清晰区分

---

## 5. 需求拆分建议

建议拆成两个阶段：

### 第一阶段：安装形态收口

1. 验证执行端能否稳定通过 `npm pack` / `npm install -g ./xxx.tgz` 安装  
2. 沉淀最小安装步骤  
3. 确认 daemon、auth、tmux 在安装包方式下可正常工作

### 第二阶段：品牌化命名

1. 修改 npm 包名  
2. 评估是否同步修改 CLI 命令名  
3. 同步梳理手机浏览器、原生 App、Mac 执行端的用户术语  
4. 把 GitHub 仓库相关对外展示与跳转统一切到 `dongaiqiang/hellovibe`
5. 处理发布、文档、升级兼容、旧命令迁移等问题

---

## 6. 验收标准

1. 不给源码仓库时，目标机器仍可安装执行端  
2. 目标机器可通过安装包完成 auth、daemon start、daemon status  
3. 执行端安装后仍能作为 Open in Mac 的执行节点使用  
4. 若启用自定义品牌名，安装命令与实际 CLI 命令语义一致  
5. 不出现“包名已变、命令仍混乱、用户无法判断使用哪个命令”的交付问题  
6. 关键入口文案能让普通用户区分“新建账号、恢复账号、让 Mac 加入账号、把会话切到 Mac”  
7. GitHub 仓库展示、Issue 跳转、Terms 链接等对外仓库引用统一指向 `dongaiqiang/hellovibe`
8. 若后续启用新 CLI 品牌名，安装命令、更新命令、诊断命令与实际可执行命令保持一致，不出现“界面已写 hellovibe，但终端仍只能执行 happy”的割裂
9. Mac 远程模式终端界面在常见使用场景下保持基本整洁，不出现明显的错行、重叠或状态混乱

## 9. 当前进度（更新于 2026-04-05）

截至 2026-04-05，当前整体判断不是“这件事还完全没开始”，而是：

1. 执行端 npm 化的基础骨架已经具备  
2. `tgz` 打包能力已经初步打通  
3. 但对外交付所需的收口还没有完成  
4. 品牌化命名、仓库展示切换、术语统一基本还没进入正式实施

### 9.1 已完成

目前已经确认完成或基本成立的部分包括：

1. `packages/happy-cli/package.json` 已具备 npm 包基础结构  
2. 当前包已经存在 `bin`、`files`、`prepublishOnly`、`postinstall` 等发布相关配置  
3. 当前 CLI 入口脚本已经具备可执行包装形式，不是只能在源码环境下跑  
4. 当前执行端可以完成构建  
5. 当前执行端已经可以执行 `npm pack --dry-run`，说明 `tgz` 打包路径基本成立

### 9.2 已确认的现状

当前核实到的实际状态如下：

1. 目录名虽然是 `packages/happy-cli`，但 workspace 实际名称仍是 `happy-coder`  
2. 当前 npm 包名仍是 `happy-coder`  
3. 当前 CLI 命令入口仍是 `happy`、`happy-mcp`

### 9.3 仍未完成

以下事项截至 2026-04-05 仍未完成：

1. `npm install -g ./xxx.tgz` 的完整交付验收还没有形成最终闭环  
2. `npm install -g 包名` 的正式发布路径还没有落地  
3. 包名从 `happy-coder` 切换到 `hellovibe-coder` 或 `hellovibe-cli` 尚未实施  
4. CLI 命令从 `happy` 切换到 `hellovibe` 尚未实施  
5. GitHub 对外展示、仓库归属、Issue/链接等元信息切到 `dongaiqiang/hellovibe` 尚未完成  
6. 手机浏览器、原生 App、Mac 执行端相关术语统一尚未完成  
7. Mac 远程模式终端整洁度问题尚未作为本需求正式收口

### 9.4 当前已暴露的问题

当前第一阶段推进中，已经明确暴露出以下收口问题：

1. `npm pack --dry-run` 虽然可用，但产物体积仍然偏大  
2. 打包内容里仍混入了不应直接作为最终交付内容暴露的二进制/工具产物  
3. workspace 名、包名、命令名、仓库展示名仍然混杂  
4. 当前更像研发可验证形态，还不是正式产品交付形态

### 9.5 当前阶段结论

如果用一句人话描述当前状态，更准确的说法应是：

1. 不是“npm 还没开始做”

换句话说，当前不是 0 到 1 还没开始，而是：

1. 第一阶段已经推进了一半左右

### 9.6 下一步最小闭环

当前最合理的下一步，不是立刻全面品牌化，而是先把第一阶段真正收口。

建议按以下顺序推进：

## 10. 第一阶段剩余执行清单

为了让这份文档不只停留在“进度判断”，这里把第一阶段剩余工作进一步落成可执行清单。

当前建议只围绕“安装形态收口”推进，不把品牌化命名混进本阶段。

### 10.1 P0：必须先完成

这一批完成前，不能把当前状态定义成“已经具备正式对外交付能力”。

#### 1. 跑通一次真实 `tgz` 安装闭环

目标：

1. 不是只验证 `npm pack --dry-run`  
2. 而是要真实生成 `.tgz`，并在干净目录或临时前缀中完成安装

执行要点：

1. 本地生成正式 `.tgz` 包  
2. 使用 `npm install -g ./xxx.tgz` 或等价临时前缀方式安装  
3. 安装后实际执行 CLI 命令  
4. 确认命令入口、依赖展开、启动流程都能正常工作

完成标准：

1. 能真实安装  
2. 能真实执行  
3. 安装后不是只能看到文件存在，而是命令可用

#### 2. 收口 npm 包内容

目标：

1. 解决当前 tarball 体积偏大的问题  
2. 解决不必要的工具产物、解包文件被混入安装包的问题

执行要点：

1. 核对 `files`、`.npmignore`、构建产物边界  
2. 明确哪些内容必须进包  
3. 明确哪些内容应通过安装后解包、运行时下载或其他机制处理  
4. 避免把研发内部工具、临时二进制、非必要大文件直接带进最终交付包

完成标准：

1. 包内容边界清楚  
2. 包体积明显收敛  
3. 交付包内容能解释清楚“为什么这些文件必须存在”

#### 3. 验证安装包方式下的运行链路

目标：

确认执行端在“安装包形态”下仍保留核心能力，而不是只有命令能启动。

执行要点：

1. 验证 `auth`  
2. 验证 `daemon start`  
3. 验证 `daemon status`  
4. 验证 `tmux` 托管相关能力  
5. 验证与当前 Server / Web 链路配合是否正常

完成标准：

1. 安装包方式下，核心执行链路能跑通  
2. 不出现“源码运行可用、安装包运行不可用”的割裂

### 10.2 P1：第一阶段建议补齐

这一批不一定阻塞最小闭环，但建议在第一阶段内尽量完成。

#### 1. 沉淀最小安装步骤

目标：

1. 把当前安装路径整理成稳定、可复用、对外可讲清楚的步骤

至少应明确：

1. 如何生成包  
2. 如何安装包  
3. 如何首次登录  
4. 如何启动 daemon  
5. 如何检查状态  
6. 如何做最小排错

#### 2. 区分研发安装形态与交付安装形态

目标：

1. 明确源码开发方式和对外交付方式不是一回事  
2. 避免后续又把“研发运行流程”直接当成“用户安装流程”

建议至少划清两类：

1. 研发调试版：源码、workspace、联调  
2. 对外交付版：tgz / npm 包、最小安装步骤、最小运行闭环

#### 3. 明确第一阶段不改什么

目标：

防止执行时边界继续扩散。

当前建议明确不纳入第一阶段的事项：

1. 包名正式切换到 `hellovibe-*`  
2. CLI 命令正式切换到 `hellovibe`  
3. GitHub 对外展示整体改名  
4. 手机端与桌面端全部术语统一  
5. Mac 远程模式视觉与终端整洁度的整体体验收口

### 10.3 推荐执行顺序

建议按下面顺序推进第一阶段：

1. 先跑真安装闭环  
2. 再收口包内容  
3. 再验证运行链路  
4. 再整理最小安装步骤

### 10.4 第一阶段完成判断

满足以下条件后，才能把第一阶段定义为“基本完成”：
