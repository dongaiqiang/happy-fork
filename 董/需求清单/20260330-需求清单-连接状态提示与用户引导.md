# 20260330 需求清单：连接状态提示与用户引导

## 1. 文档目的

本需求文档聚焦一个产品问题：

- 当前 App 内存在多种“连接/在线”语义
- 但用户界面上的提示还不够清楚
- 用户容易分不清：
  - App 是否连上 Happy 服务
  - 电脑 daemon 是否在线
  - machine 是否仍可远程控制
  - 当前 session 是否仍然活着

本需求的目标，是把这些状态用用户能理解的方式表达出来，并在关键场景下明确提示“下一步该做什么”。

---

## 2. 业务背景

本轮真机验证中，已经确认以下行为都属于当前架构下的正常现象：

1. daemon 停掉后，已有 session 仍可能继续对话
2. daemon 停掉后，新建 session 会失败
3. daemon 停掉后，machine 在某些页面里不是简单变成 offline，而是会直接从机器列表消失
4. 设置页顶部仍可能显示“已连接”，因为那表示的是 App ↔ Server 的连接仍在

这些行为对开发者来说可以解释，但对普通用户来说非常绕。

用户的真实困惑通常不是“active flag 变了吗”，而是：

- 我现在到底还能不能新建会话？
- 这台电脑是不是坏了？
- 为什么我还能继续聊，但机器又没了？
- 我接下来应该回电脑上干什么？

因此，本需求不追求展示更多技术状态，而是追求：

- 降低歧义
- 用用户语言解释当前情况
- 给出明确下一步动作

---

## 3. 核心需求：状态语义澄清 + 下一步动作提示

## 3.1 需求描述

在设置页、机器页、会话页、新建 session 失败提示等关键位置，为用户提供：

1. 更准确的状态文案
2. 更清晰的状态层级
3. 更直观的状态指示组件
4. 更明确的下一步动作建议

目标不是让用户理解系统架构，而是让用户明白：

- 现在发生了什么
- 这意味着什么
- 下一步应该做什么

## 3.2 用户价值

1. 减少“已连接 / 在线 / 离线 / 会话仍可继续”之间的误解  
2. 降低故障时的焦虑和盲试成本  
3. 让用户在无需理解 daemon / session 架构的情况下完成自助恢复  
4. 提高新建 session、设备切换、后台恢复等场景的可解释性

---

## 4. 产品语义分层

本需求建议后续在产品语义上明确区分以下四类状态：

### 4.1 服务连接状态

表示：

- App 是否已经连接到 Happy 服务端

用户语言建议：

- `已连接到 Happy 服务`
- `正在连接到 Happy 服务`
- `已断开与 Happy 服务的连接`

### 4.2 电脑可控状态

表示：

- 某台电脑当前是否可被远程新建/管理 session

用户语言建议：

- `这台电脑当前可新建会话`
- `这台电脑当前不可新建会话`

### 4.3 当前会话状态

表示：

- 当前会话本身是否仍在运行、能否继续对话

用户语言建议：

- `当前会话仍在运行`
- `当前会话已停止`

### 4.4 下一步动作提示

表示：

- 遇到当前状态后，用户应该采取什么行动

用户语言建议：

- `请回到电脑上启动后台进程`
- `已有会话可能仍可继续`
- `后台进程恢复后可重新新建会话`

---

## 5. 圆形状态指示设计（本期纳入需求）

本需求建议引入或统一使用一个**圆形状态指示**，作为用户对状态的第一感知入口。

这里的“圆形”不是单独表达所有含义，而是作为状态层级中的一个视觉辅助。

### 5.1 设计目标

圆形状态指示要表达的是“当前主状态”，但不能独立承担全部语义，必须配合文字说明使用。

### 5.2 使用原则

1. 圆形指示只做快速感知，不单独承担复杂语义  
2. 圆形颜色必须配合文字标题  
3. 圆形下方或旁边必须有一句人话解释  
4. 复杂场景必须附带“下一步动作”

### 5.3 建议语义

- 绿色圆形：当前主状态正常
- 黄色圆形：当前部分可用，但存在限制
- 灰色圆形：当前不可用或状态未知
- 红色圆形：明确异常，需要处理

### 5.4 典型场景

#### 场景 A：App 已连接服务端

- 圆形：绿色
- 文案：`已连接到 Happy 服务`

#### 场景 B：App 连着服务端，但电脑 daemon 不在线

- 圆形：黄色
- 文案：`服务已连接，但这台电脑当前不可新建会话`
- 补充：`已有会话可能仍可继续`
- 动作：`请在电脑上启动后台进程`

#### 场景 C：当前会话还活着，但 machine 已不可控

- 圆形：黄色
- 文案：`当前会话仍在运行`
- 补充：`但这台电脑当前不可新建新会话`

#### 场景 D：服务端连接本身已断开

- 圆形：红色或灰色
- 文案：`已断开与 Happy 服务的连接`
- 动作：`请检查网络或服务地址`

## 6. 页面级需求

## 6.1 设置页

### 当前问题

顶部“已连接”过于笼统，用户容易误解为：

- 电脑 daemon 也在线
- machine 也可控
- 一切都正常

### 需求

设置页顶部需要明确表达：

- 这是 App ↔ Server 的连接状态
- 不直接代表 daemon 在线或 machine 可控

### 建议方向

1. 顶部主文案从泛化的“已连接”升级为：
   - `已连接到 Happy 服务`
2. 增加一行弱提示：
   - `电脑状态请查看下方设备列表`
3. 当当前没有可控机器时，提示：
   - `已连接到服务，但当前没有可控电脑`
4. 同时给动作建议：
   - `请在电脑上启动后台进程后重试`

### 验收标准

1. 用户在设置页顶部看到的状态，不再天然理解为 daemon 在线  
2. 用户能区分“服务已连接”和“电脑可控”是两件事  
3. 当没有活跃 machine 时，用户知道下一步该去电脑端处理

---

## 6.2 机器页 / 机器列表

### 当前问题

当前很多机器列表只显示 active 机器，导致 machine 一旦不活跃，就会直接从列表中消失。

用户看到的效果是：

- 这台 Mac 没了

而不是：

- 这台 Mac 离线了

### 需求

机器页应尽可能降低“机器突然消失”的突兀感，并用人话说明当前限制。

### 建议方向

1. 优先方案：
   - 不活跃 machine 保留展示一段时间，状态标记为 `离线`
2. 兼容方案：
   - 如果当前产品逻辑仍然只展示 active 机器，则应在相关页面补充说明：
     - `该电脑当前未上报为活跃设备`
3. machine 详情页增加状态解释：
   - `这台电脑当前不可新建会话`
   - `已有会话可能仍在继续运行`
4. 增加下一步动作：
   - `请在电脑上启动 happy daemon`

### 验收标准

1. 用户不会把“机器从列表消失”误以为“数据丢了”  
2. 用户能理解“电脑不可控”不等于“已有会话全部终止”  
3. 页面能给出明确恢复动作

---

## 6.3 新建 session 页

### 当前问题

daemon 不在线时，新建 session 失败，对用户来说往往只是“失败了”，但不知道为什么失败。

### 需求

新建 session 失败时，必须优先用产品语言解释原因，而不是只给技术结果。

### 建议方向

1. 主提示：
   - `这台电脑当前无法新建会话`
2. 解释说明：
   - `电脑后台进程当前未在线`
3. 补充说明：
   - `已有会话可能仍可继续`
4. 下一步动作：
   - `请回到电脑上启动后台进程后再试`

### 验收标准

1. 用户能区分“新建失败”与“服务断网”是两类不同问题  
2. 用户知道该去电脑端处理，而不是继续盲点重试  
3. 文案不要求用户理解 daemon 架构，也能知道下一步动作

---

## 6.4 当前会话页

### 当前问题

当前最反直觉的场景是：

- machine 已不可控
- 但当前 session 仍然能继续聊

如果页面不解释，用户会自然认为系统前后矛盾。

### 需求

在检测到“当前会话仍活跃，但 machine 不可新建会话”的组合状态时，应向用户明确说明这不是冲突，而是状态分层不同。

### 建议方向

1. 主提示：
   - `当前会话仍在运行`
2. 补充说明：
   - `但这台电脑当前不可新建新会话`
3. 弱提示：
   - `如需新建会话，请先在电脑上恢复后台进程`

### 验收标准

1. 用户不会误以为系统状态自相矛盾  
2. 用户知道“当前会话可继续”不等于“整台电脑一切正常”  
3. 用户知道要去电脑端恢复什么

---

## 7. 产品原则

后续所有状态提示建议遵循以下原则：

1. **谁和谁连接，必须说清楚**  
   - 不再使用一个“已连接”覆盖所有含义

2. **状态必须带解释**  
   - 不只写 connected / offline / failed

3. **状态必须带动作**  
   - 告诉用户下一步做什么，而不是让用户自己猜

4. **技术状态要翻译成用户可执行状态**  
   - 不要求用户理解 machine-scoped / session-scoped / daemon lifecycle

---

## 8. 验收标准（整体）

1. 用户能区分：
   - App 是否连上服务端
   - 电脑是否可新建会话
   - 当前会话是否仍在运行
2. 当 daemon 不在线时，用户能明确知道为什么新建 session 失败
3. 当已有 session 仍活着时，用户不会因为 machine 消失而误以为数据异常
4. 至少在设置页、机器页、新建 session 页、当前会话页四个关键位置完成状态语义澄清
5. 圆形状态指示与文字说明搭配使用，不能只靠颜色表达复杂含义

---

## 9. 非目标（本期不做）

1. 本期不要求彻底重构 daemon / session 底层架构  
2. 本期不要求用户理解全部技术状态机  
3. 本期不要求一次性覆盖所有页面和所有异常路径  
4. 本期重点是减少歧义和补足动作引导

---

## 10. 交付优先级建议

1. P1：新建 session 失败提示改造  
2. P2：设置页顶部连接状态语义澄清  
3. P3：当前会话页“会话仍活跃但机器不可控”提示  
4. P4：机器列表/机器页对 inactive machine 的展示优化

## 12. 结论

本次结论：

- 把“连接状态提示与下一步动作引导”作为一个明确产品需求纳入后续排期
- 重点不是增加更多技术状态词，而是把技术状态翻译成用户可执行状态
- 同时把圆形状态指示纳入设计范围，但必须与文案解释和动作提示配合使用
