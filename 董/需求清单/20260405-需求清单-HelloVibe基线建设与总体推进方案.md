# 20260405 需求清单：HelloVibe 基线建设与总体推进方案

## 1. 文档目的

这份文档不聚焦某一个单点功能，而是聚焦 HelloVibe 当前阶段的整体基线建设。

这里要解决的问题不是“先改哪一个页面”或“先修哪一个接口”，而是：

1. HelloVibe 远端仓库是否从现在开始正式承接后续开发  
2. 当前工程是否已经具备进入正式协作与版本管理的条件  
3. npm 安装、品牌统一、多 Agent 协作这几件事如何放到同一个框架里推进  
4. 哪些工作应该先做，哪些工作可以并行，哪些工作应后置  
5. 后续如何在不把工程搞乱的前提下，把整体推进速度提起来

因此，这份文档的定位是：

1. HelloVibe 当前阶段的总纲文档  
2. 后续专项需求并行推进的上层依据  
3. 多 Agent 接入后的调度参考文档

关联文档：

1. 执行端安装与品牌专项见《20260401 需求清单：执行端 NPM 安装与品牌化命名》  
2. 多 Agent 协作规则见《20260405 需求清单：多 Agent 协作制度清单》  
3. 仓库迁移专项见《20260405 需求清单：迁到 HelloVibe 仓库推进方案》

使用方式建议：

1. 先用本文档判断 HelloVibe 当前整体阶段、主线和优先级  
2. 涉及仓库切换、迁移顺序、SoEasyWork 与 HelloVibe 关系时，进入迁仓专项文档  
3. 再按主题进入 npm / 品牌专项文档或多 Agent 制度文档  
4. 具体执行时，以专项文档和协作制度文档作为落地依据

## 2. 当前背景

当前项目已经具备以下现实前提：

1. 远端私有仓库 `dongaiqiang/HelloVibe` 已经建立  
2. 本地工程已经持续开发，并已有多批代码改动与联调成果  
3. 执行端 npm 安装与品牌化命名已经形成独立专项需求  
4. Open in Mac、Server、CLI、App 等核心链路已经不再是纯概念阶段  
5. 后续计划引入 Claude Code、Codex 等 Agent 参与协作  
6. 项目目标已经从“单人单工具推进”转向“多人 + 多 Agent 并行推进”

这说明后续最重要的事情，已经不是单纯再做几个功能，而是把 HelloVibe 从“正在开发的工程”升级为“可以被持续协作、持续提交、持续收口的正式产品仓库”。

---

## 3. 当前总判断

当前整体状态，可以概括为以下三点：

1. 已经具备进入正式仓库管理与持续协作的条件  
2. 但还不适合把当前整个工作区原样一次性整体提交  
3. 当前最需要的不是追求一次性成品化，而是先形成一个可协作、可并行推进的基线版本

更直白一点说：

1. 现在已经不是“先别进仓库”的阶段  
2. 但也不是“什么都不分就直接一把推上去”的阶段  
3. 当前最合理的目标，是先建立 HelloVibe 协作基线，再在这个基线上并行推进 npm、品牌和多 Agent 协作

---

## 4. 基线建设目标

当前阶段建议把目标收敛为四项。

### 4.1 远端仓库正式化

目标：

1. 让 `dongaiqiang/HelloVibe` 成为后续开发的唯一正式远端承接仓库  
2. 把当前成果逐步纳入版本管理  
3. 形成后续多人和多 Agent 协作的共同真相源

### 4.2 执行端交付标准化

目标：

1. 让执行端逐步脱离“必须依赖源码仓库运行”的状态  
2. 形成 `tgz` / npm 安装能力  
3. 为后续对外交付、标准安装和复用部署打基础

### 4.3 HelloVibe 品牌统一路径明确化

目标：

1. 明确 HelloVibe 是唯一对外品牌方向  
2. 把仓库、npm 包、CLI 命令、产品术语的统一顺序排清楚  
3. 不在当前阶段一口气全量改名，而是按阶段推进

### 4.4 多 Agent 协作机制建立

目标：

1. 让 Trae、Claude Code、Codex 等 Agent 可以稳定协同  
2. 建立 owner、边界、handoff、review 和并行推进的基本制度  
3. 让后续速度提升建立在规则之上，而不是建立在混乱之上

---

## 5. 四条主线

基于当前目标，后续工作建议按四条主线推进。

### 5.1 主线 A：仓库与版本管理

这条主线解决的是：

1. 远端仓库正式启用  
2. 当前工作区边界收口  
3. 哪些内容属于正式成果  
4. 哪些内容不应混入正式提交  
5. 后续采用什么节奏持续进入远端仓库

这条线的价值在于：

1. 为后续所有并行工作建立共同基线  
2. 降低后面越来越多改动无法回收的风险  
3. 让项目从“本地状态驱动”转向“仓库状态驱动”

### 5.2 主线 B：执行端 npm / tgz 交付

这条主线解决的是：

1. 执行端是否能不依赖源码仓库安装  
2. `npm pack` / `.tgz` 是否真正可用  
3. 安装后 `auth`、`daemon`、`tmux` 是否能正常工作  
4. 交付包内容是否已经收口

这条线的价值在于：

1. 它不只是安装问题，而是产品交付能力问题  
2. 它会直接影响后续部署、测试和外部交付方式  
3. 它是 HelloVibe 工程产品化的重要基线之一

### 5.3 主线 C：HelloVibe 品牌统一

这条主线解决的是：

1. 对外品牌统一为 HelloVibe  
2. 仓库展示、npm 包名、CLI 命令名逐步统一  
3. 手机端、原生 App、Mac 执行端的用户术语逐步统一  
4. 历史命名如何分阶段迁移，而不是一次性硬改

这条线的价值在于：

1. 避免对外看到多套名字混杂  
2. 让安装、命令、品牌与用户体验逐步一致  
3. 为后续正式对外展示和产品化表达打基础

### 5.4 主线 D：多 Agent 协作机制

这条主线解决的是：

1. Trae、Claude Code、Codex 如何进入同一个工程协作  
2. 哪些任务可以并行，哪些任务必须串行  
3. 谁负责主调度，谁负责主实现，谁负责 review  
4. 多 Agent 协作如何不把仓库节奏搞乱

这条线的价值在于：

1. 后续很多工作可以并行开始  
2. 并行的前提是有边界和规则  
3. 这条线决定后面速度能不能真正提升

## 6. 阶段划分

为了避免所有事情同时开、最后全部失焦，建议按三个阶段推进。

### 6.1 阶段一：协作基线建立

这一阶段的目标不是“把所有事做完”，而是先搭起一个正式可持续推进的底座。

重点包括：

1. 远端 HelloVibe 仓库正式作为主承接仓库  
2. 当前工作区边界收口  
3. 形成第一版可协作基线  
4. 确认专项需求文档与总纲文档的关系  
5. 确认多 Agent 协作基本规则

### 6.2 阶段二：双主线并行推进

阶段一稳定后，建议至少启动两条主线并行：

1. 执行端 npm / tgz 交付主线  
2. HelloVibe 品牌统一主线

这里强调的是：

1. 两条主线并行  
2. 但每条主线仍然要有明确 owner  
3. 不把两条主线混成一次大改动

### 6.3 阶段三：多 Agent 常态化协作

当仓库、文档、分工和主线都建立起来后，再让多 Agent 协作进入常态。

这一阶段重点包括：

1. 任务分发稳定化  
2. handoff 模板稳定化  
3. review 机制稳定化  
4. 并行推进常态化

---

## 7. 当前阶段优先级

基于当前实际情况，建议优先级按以下顺序排列：

### 第一优先级：仓库正式化与提交边界收口

原因：

1. 如果连正式基线都没有，后面并行越多越乱  
2. 当前已经积累了较多改动，不宜继续长期悬空

### 第二优先级：执行端 npm / tgz 交付闭环

原因：

1. 这是执行端产品化交付的核心问题  
2. 也是后续品牌统一和对外交付的重要基础

### 第三优先级：品牌统一分阶段推进

原因：

1. 品牌统一重要，但不适合在当前阶段一次性全量硬切  
2. 应先明确顺序，再逐步推进

### 第四优先级：多 Agent 常态化并行

原因：

1. 多 Agent 能提速，但前提是基线稳定  
2. 先有规则，再扩大并行，整体效率更高

## 8. 多 Agent 分工建议

在 HelloVibe 基线建设阶段，建议采用以下协作方式。

### 8.1 Trae

建议承担：

1. 主调度  
2. 主开发  
3. 联调推进  
4. 跨文件修复  
5. 合并前集成判断

### 8.2 Claude Code

建议承担：

1. 方案设计  
2. 架构建议  
3. 品牌与术语收口建议  
4. 代码 review  
5. 测试补强建议  
6. 风险二次分析

### 8.3 Codex

建议承担：

1. 脚本与工具链补位  
2. 局部模块实现  
3. 测试样例  
4. 打包边界梳理  
5. 辅助性工程任务

### 8.4 基本协作规则

建议固定以下规则：

1. 一个任务只有一个主 owner  
2. 一个文件同一时段只有一个主编辑者  
3. 多个 Agent 可以并行给方案，但不能同时主写同一块代码  
4. review 与实现尽量分角色  
5. 所有结果最终统一回收到同一个仓库节奏里

## 10. 当前建议的推进方式

当前阶段不建议追求“一次性做成最终成品”，而建议采用以下推进方式：

1. 先把 HelloVibe 仓库正式化  
2. 先形成一版可协作基线  
3. 在这个基线上同时启动 npm 交付主线与品牌统一主线  
4. 让多 Agent 围绕明确 owner 和明确边界参与  
5. 逐步把本地连续工作沉淀成正式仓库历史

这个推进方式的核心不是“看起来快”，而是：

1. 每一步都能回收到仓库  
2. 每一步都能接得住更多人和更多 Agent  
3. 每一步都能为下一步并行创造条件

## 11. 建议的提交分批策略

为了让 HelloVibe 远端仓库尽快进入正式承接状态，同时避免一次性把当前混杂工作区整体推上去，建议按三批提交。

### 11.1 第一批：协作基线批

目标：

1. 先把后续并行推进必须依赖的基线内容进入仓库  
2. 让远端仓库先承接“可持续协作能力”，而不是先承接所有零散改动

建议优先纳入：

1. 已经稳定、已形成明确结论的需求文档  
2. 已经验证通过的主链路修复  
3. 当前继续开发必须依赖的基础工程调整

这一批的要求是：

1. 主题要集中  
2. 改动边界要清楚  
3. 能作为后续并行推进的共同起点

### 11.2 第二批：执行端交付批

目标：

1. 把执行端 `tgz` / npm 交付主线按专项节奏逐步进入仓库  
2. 每次只提交一个明确闭环，而不是把打包、品牌、术语同时混进来

建议按以下顺序进入：

1. 真实 `tgz` 安装闭环  
2. 包内容收口与体积瘦身  
3. 安装包方式下 `auth`、`daemon`、`tmux` 运行链路验证

这一批的要求是：

1. 一个提交只承接一个可验收结果  
2. 每次进入仓库前都要有对应验证结论  
3. 不把未验证的品牌化改名混入交付主线

### 11.3 第三批：品牌统一批

目标：

1. 在仓库基线和执行端交付基线稳定后，再逐步推进 HelloVibe 品牌统一  
2. 把仓库展示、npm 包名、CLI 命令名、用户术语分阶段纳入正式历史

建议按以下顺序进入：

1. 仓库展示与对外链接统一  
2. npm 包名切换  
3. CLI 命令名切换  
4. 多端用户术语统一

这一批的要求是：

1. 先解决对外一致性，再处理历史兼容  
2. 每次命名变更都要说明影响范围  
3. 不把多个大范围改名压成一个不可 review 的超大提交

### 11.4 分批策略的核心原则

1. 先立基线，再做专项，再做统一改名  
2. 先提交已验证结论，不提交混杂中的临时状态  
3. 提交粒度按“可验收主题”切，而不是按“今天改了多少文件”切

## 12. 验收标准

这份总纲文档所对应的阶段性验收，不是看某个单点功能，而是看基线是否已经立住。

建议按以下标准判断：

1. HelloVibe 远端仓库已经正式承接后续开发  
2. 当前成果能够按主题清晰进入版本管理  
3. 执行端 npm / tgz 交付主线已经进入实做与验证阶段  
4. 品牌统一主线已经形成清晰阶段方案，而不是停留在口头讨论  
5. 多 Agent 协作已经具备明确的角色、边界和基本调度方式  
6. 后续新增 Agent 或新增专项需求，不需要重新发明整套推进机制

## 14. 结论

当前最合理的整体路径，不是把 npm、品牌、多 Agent、仓库提交这几件事拆开各自零散推进，而是把它们统一纳入 HelloVibe 基线建设阶段。

这一阶段的核心目标可以概括为：

1. 让 HelloVibe 仓库成为正式真相源  
2. 让执行端交付开始标准化  
3. 让品牌统一具备清晰路径  
4. 让多 Agent 协作具备可持续规则  
5. 在此基础上，把后续很多工作真正并行启动起来

一句话总结就是：

先建立 HelloVibe 协作基线，再在这个基线上并行推进 npm 交付、品牌统一和多 Agent 协作，这样后面的整体速度才会真正提升。
