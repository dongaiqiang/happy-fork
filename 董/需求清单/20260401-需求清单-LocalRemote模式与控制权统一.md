# 20260401 需求清单：Local / Remote 模式与控制权语义统一

## 1. 文档目的

本需求文档聚焦一个新的产品问题：

- 当前终端内的 `local / remote` 模式切换
- 与 Happy 会话的 `mobile / mac` 控制权切换
- 在产品语义上还没有完全统一

本需求的目标，是把这两套概念收敛为用户能直觉理解的一套行为定义，避免出现“看起来已经切过去了，但真实控制权没切”的中间态。

---

## 2. 问题背景

当前 Open in Mac 的整体主链已经基本可用：

1. Mac 与手机双端消息同步整体正常  
2. 双端切换时，新增信息可以明显同步过来  
3. Hosted / tmux 承载下，终端内会出现：
   - `Press space to switch to local mode • Ctrl-C to exit`

但这里暴露出一个新的产品问题：

1. 终端内的 `switch to local mode`
2. 与手机端的“切换控制权到 Mac / 切回手机”

用户感知上并不是同一件事。

这会带来理解成本：

- 用户会以为“切到 local mode”就等于“Mac 已经正式接管”
- 但系统内部可能只是 CLI 展示/运行模式切换
- 未必已经完成会话级 controller 的切换

因此需要把这部分单独定义清楚，并纳入后续研发排期。

---

## 3. 核心需求

## 3.1 需求描述

在 Open in Mac 的最终产品形态里：

1. `local / remote` 不应只是 CLI 内部模式概念  
2. 它应与 `mac / mobile controller` 的产品语义保持一致  
3. 用户执行模式切换时，应同时完成真实控制权切换  
4. 不允许长期存在“模式已切换、控制权未切换”的半状态

## 3.2 用户价值

1. 降低理解成本，用户不用区分两套概念  
2. 保证“谁可输入、谁可审批、谁只读”始终一致  
3. 避免切换后出现权限、输入、展示语义错位  
4. 让 Open in Mac 更接近“Mac 原生 Claude + tmux 托管”的最终产品目标

## 3.3 功能定义

### A. 从 remote 切到 local

当用户在 Hosted / tmux 场景下执行 `switch to local mode` 时，产品语义应为：

1. Mac 取得控制权  
2. 手机端进入只读观察态  
3. Mac 端进入可交互的本地 Claude 使用态  
4. 后续权限审批与输入控制默认归 Mac

### B. 从 local 切回 remote

当用户切回 remote mode 时，产品语义应为：

1. 手机取得控制权  
2. Mac 端进入只读观察态  
3. 手机端恢复可输入、可操作、可审批  
4. Mac 端只承担观察/查看同步内容的角色

### C. 错误与异常语义

1. 如果模式切换成功，但控制权切换失败，不能假装成功  
2. 界面必须明确提示当前真实控制方  
3. 系统应尽量避免进入“CLI 已 local、controller 仍是 mobile”这类中间态  
4. 如果确实发生异常中间态，需要给出恢复路径或重试提示

---

## 4. 产品原则

1. 单一语义：用户只需要理解“当前谁在控制”  
2. 双端可见：手机与 Mac 仍可同时看到同一会话内容  
3. 单端可控：任意时刻仅一个控制端可写入和执行  
4. 切换原子化：模式切换与控制权切换应尽量作为一个完整动作完成  
5. 状态透明：一旦失败，要明确告诉用户真实状态，不制造错觉

---

## 5. 验收标准

1. 用户在终端执行 `switch to local mode` 后，Mac 真实成为控制端  
2. 用户切回 remote mode 后，手机真实成为控制端  
3. 切换完成后，输入权、审批权、只读态三者保持一致  
4. 双端消息同步在切换前后保持连续  
5. 不出现长期可见的半状态  
6. 若切换失败，界面可明确说明当前 controller 与失败原因

---

## 6. 非目标

1. 不支持双端同时写入  
2. 不在本需求中扩展多设备抢占策略  
3. 不在本需求中处理更广泛的 session 生命周期重构  
4. 不把 Happy 的 remote 观察视图替代为最终 Claude 原生终端产品形态

---

## 7. 与现有需求的关系

1. 本文档是一个新的独立需求，不并入既有 Open in Mac 需求正文  
2. 它与 Open in Mac 强相关，但关注点更细：
   - 不是“能不能打开到 Mac”
   - 而是“local / remote 与控制权语义是否彻底统一”
3. 后续实现时，可作为 Open in Mac 第二阶段体验收口需求处理

---

## 8. 结论

本次结论：

- 单独新增一份需求清单，专门定义 `local / remote` 与 `mobile / mac controller` 的统一语义  
- 后续研发按“模式切换 = 控制权切换”的方向收口  
- 在进入阿里云部署架构阶段前，先把该问题明确沉淀为独立产品需求
