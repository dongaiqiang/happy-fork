# 20260405 需求清单：多 Agent 协作制度清单

## 1. 文档目的

这份文档只解决一件事：

把当前研发协作方式，从“单个 Agent 辅助开发”，升级为“多个 Agent 在同一仓库下协作开发”的制度化方案。

这里的多个 Agent，当前已明确包括：

1. Trae  
2. Claude Code  
3. Codex（后续可能加入）  
4. 未来其他同类 Agent

这份文档不是技术实现方案，也不是具体工具安装教程。

它更偏协作制度设计，回答以下问题：

1. 多个 Agent 应该如何分工  
2. 多个 Agent 应该如何进入同一个仓库协作  
3. 哪些工作可以并行，哪些工作必须串行  
4. 出现冲突、重复改动、边界不清时，应该按什么规则处理  
5. 后续 Agent 数量继续增加时，体系如何不失控

关联文档：

1. 上层总纲文档见《20260405 需求清单：HelloVibe 基线建设与总体推进方案》  
2. 仓库迁移专项见《20260405 需求清单：迁到 HelloVibe 仓库推进方案》  
3. 执行端安装与品牌专项见《20260401 需求清单：执行端 NPM 安装与品牌化命名》  
4. 本文档聚焦协作制度，不替代具体业务专项文档

使用方式建议：

1. 先用总纲文档判断当前属于哪条主线、哪个阶段  
2. 涉及 SoEasyWork 与 HelloVibe 切换时，先到迁仓专项文档确认迁移边界  
3. 再用本文档确定 owner、handoff、review 和并行边界  
4. 进入具体实现时，再回到对应专项文档执行

## 2. 当前背景

当前工程已经具备以下现实前提：

1. 远端代码仓库已经建立  
2. 仓库中已经有若干历史提交  
3. Trae 已经在持续参与实际开发  
4. 后续计划引入 Claude Code  
5. 再后续 Codex 也可能加入  
6. 未来不排除继续接入更多智能体

这意味着后续要管理的，已经不是“一个 AI 工具怎么帮忙写代码”，而是“多个数字执行体如何在同一工程中稳定协作”。

如果不先建立制度，随着 Agent 增加，极容易出现以下问题：

1. 同一个需求被多个 Agent 同时改写  
2. 同一个文件被不同 Agent 来回覆盖  
3. 每个 Agent 的命名风格、改动粒度、验证标准不一致  
4. 人需要反复做上下文转述，调度成本越来越高  
5. 最后虽然看起来效率变高，实际上仓库可维护性下降

因此，多 Agent 协作必须先定规则，再扩大规模。

---

## 3. 总体原则

多 Agent 协作的底层原则建议固定为以下八条：

1. 远端仓库是唯一真相源  
2. 一个任务只能有一个主负责人  
3. 一个文件在同一时段只能有一个主编辑者  
4. 一个阶段只能有一个最终决策人  
5. Agent 可以并行给方案，但不能无边界并行改同一块代码  
6. 所有 Agent 都必须遵守同一套项目规则  
7. 所有改动都必须经过统一的验证门禁  
8. 发布、合并、敏感权限必须收口在人手里

这八条里最重要的不是“多聪明地用 AI”，而是“如何避免多智能体把项目搞乱”。

## 4. 组织模型

建议把整个协作体系拆成三层。

### 4.1 第一层：人类 Owner

由你承担以下职责：

1. 决定需求优先级  
2. 决定哪个任务进入开发  
3. 决定哪个 Agent 负责哪个任务  
4. 决定哪些结果可以合并  
5. 决定哪些高风险操作需要人工批准

也就是说，你不是单纯的消息转发员，而是整个多 Agent 系统的产品 Owner 与调度 Owner。

### 4.2 第二层：主调度 Agent

建议当前固定由 Trae 承担主调度职责。

主调度 Agent 负责：

1. 接收需求  
2. 拆分任务  
3. 指出涉及模块与风险点  
4. 判断哪些子任务可并行  
5. 汇总不同 Agent 的产出  
6. 在合并前给出整体状态判断

不建议频繁更换主调度 Agent。

原因很简单：

1. 主调度角色需要持续上下文  
2. 角色频繁切换会导致规则漂移  
3. 后续责任边界会变模糊

### 4.3 第三层：执行 Agent

执行 Agent 不需要人人平权，建议分成不同职责类型：

1. 主开发型 Agent  
2. 评审型 Agent  
3. 方案型 Agent  
4. 专项型 Agent

当前建议分工如下：

#### Trae

适合承担：

1. 主调度  
2. 主开发  
3. 跨文件修复  
4. 联调验证  
5. 合并前集成判断

#### Claude Code

适合承担：

1. 方案设计  
2. 架构建议  
3. 代码评审  
4. 重构建议  
5. 测试补强建议  
6. 风险二次分析

#### Codex

建议作为专项型或第二实现者使用，适合承担：

1. 小模块实现  
2. 脚本与工具链补位  
3. 局部代码生成  
4. 测试样例  
5. 辅助性工程任务

## 5. 协作角色制度

为了避免每个 Agent 都“什么都能干”，建议固定四类角色。

### 5.1 Orchestrator

职责：

1. 收需求  
2. 拆任务  
3. 派任务  
4. 汇总状态  
5. 控制节奏

规则：

1. 一个阶段只保留一个 Orchestrator  
2. Orchestrator 可以不直接写代码  
3. Orchestrator 必须知道每个子任务的 owner 是谁

### 5.2 Implementer

职责：

1. 改代码  
2. 控制改动范围  
3. 跑基础验证  
4. 输出实现结论

规则：

1. 一个子任务只能有一个主 Implementer  
2. Implementer 改完必须带验证结果  
3. 不允许顺手扩大需求范围

### 5.3 Reviewer

职责：

1. 看实现是否合理  
2. 看边界是否越界  
3. 看是否有更小改法  
4. 看测试是否足够  
5. 看是否符合项目风格

规则：

1. Reviewer 原则上不直接抢主写  
2. Reviewer 更偏指出问题，而不是重新发明整个方案  
3. Reviewer 发现重大偏差时，应建议退回而不是私自整体重做

### 5.4 Specialist

职责：

1. 做特定领域任务  
2. 例如发布、脚本、CI、测试、品牌化、性能、安全等专项工作

规则：

1. Specialist 只在明确边界内工作  
2. 不跨域接管主线开发  
3. 输出应尽量结构化，便于主调度 Agent 接回

## 6. 仓库协作制度

### 6.1 真相源

必须明确：

1. 远端 Git 仓库是唯一真相源  
2. 所有 Agent 的本地目录都只是工作副本  
3. 任何结论都必须能回到 Git 记录中  
4. 最终状态不能停留在聊天窗口里

### 6.2 分支制度

建议采用以下分支结构：

1. `main`：稳定、可发布  
2. `dev`：日常集成  
3. `feature/*`：新需求  
4. `fix/*`：修复类任务  
5. `spike/*`：实验、验证、预研

分支命名建议按业务或模块命名，而不是按 Agent 命名。

推荐：

1. `feature/server-session-reconnect`  
2. `feature/cli-npm-packaging`  
3. `fix/server-quota-routes`

不推荐：

1. `feature/claude-do-this`  
2. `feature/codex-try-this`

原因是仓库最终管理的是业务任务，不是模型来源。

### 6.3 工作区制度

多个 Agent 不应长期共用同一个实时目录。

建议优先级如下：

1. 一个主仓库 + 多个 worktree  
2. 多个独立 clone  
3. 最后才是多人轮流用同一目录

推荐原因：

1. 避免缓存、构建产物、依赖目录相互污染  
2. 避免端口占用和本地运行环境互相影响  
3. 避免一个 Agent 基于旧状态覆盖另一个 Agent 的新改动

---

## 7. 任务分发制度

多 Agent 协作时，建议把任务分成四类。

### 7.1 独占任务

定义：

一个任务只分配给一个 Agent 主做。

适用场景：

1. 小型 bug 修复  
2. 单接口调整  
3. 单页面改动  
4. 小范围逻辑变更

规则：

1. 不允许再派第二个 Agent 同时主写  
2. 如需补充，只能做 review 或方案建议

### 7.2 先分析后实现任务

定义：

先由一个 Agent 输出方案，再由另一个 Agent 落地。

适用场景：

1. 架构变更  
2. 品牌化改造  
3. 发布流程设计  
4. 权限体系调整  
5. 大重构

推荐流程：

1. Claude Code 先出方案  
2. Trae 再按方案落地  
3. 必要时再由 Claude 做二次 review

### 7.3 并行子任务

定义：

一个大需求拆成多个边界清楚、互不重叠的子任务，并行分派给不同 Agent。

适用场景：

1. Server 改接口 + App 接入  
2. CLI 打包 + 测试补强  
3. 代码实现 + 发布脚本 + 文案收口

制度要求：

1. 子任务必须事先拆边界  
2. 每个子任务必须只有一个 owner  
3. 不允许两个 Agent 同时修改同一组核心文件

### 7.4 竞争式咨询任务

定义：

同一个问题可以同时让多个 Agent 给方案，但不让多个 Agent 同时主写代码。

适用场景：

1. 疑难 bug 定位  
2. 性能瓶颈分析  
3. 安全风险判断  
4. 架构取舍讨论

规则：

1. 多个 Agent 可以并行给思路  
2. 最终只能选一个落地方向  
3. 选定方向后，再指定一个主实现者

## 8. 目录责任制度

如果后续 Agent 增多，建议逐步给目录设主责任人。

示例制度如下：

1. `packages/happy-server`：Trae 主负责  
2. `packages/happy-cli`：Trae 或 Codex 主负责  
3. `scripts/`：Codex 可优先承担  
4. 测试目录：Claude Code / Codex 可优先承担补强  
5. 品牌化命名、规则类文档、发布相关：Claude Code 先出方案，Trae 再统一落地

目录责任制的价值在于：

1. 降低多人改同一区域的概率  
2. 出现问题时容易追踪  
3. 便于后续做模块级并行开发

这里要强调：

目录责任制不是永久封死，而是默认优先权制度。

也就是说：

1. 默认谁更适合先接  
2. 不是说其他 Agent 永远不能碰  
3. 但跨责任域时，必须有明确任务授权

---

## 9. 规则文件制度

多 Agent 协作必须有一套统一规则，不然每个 Agent 都会带来不同工作习惯。

统一规则至少应包含以下内容：

1. 项目背景  
2. 技术栈  
3. 目录职责  
4. 启动命令  
5. 构建命令  
6. lint / typecheck / test 命令  
7. 命名规范  
8. 新增文件规则  
9. 提交规范  
10. 合并规范  
11. 敏感操作边界  
12. 哪些目录谁优先负责

制度要求：

1. 所有 Agent 读取到的规则内容必须一致  
2. 即使不同工具使用不同配置文件，核心规则也必须一致  
3. 项目规则的优先级高于单个 Agent 的默认习惯

特别需要统一的事项包括：

1. 是否允许自动新建文件  
2. 是否允许顺手重构  
3. 是否默认跑测试  
4. 是否允许改锁文件  
5. 是否允许自动提交  
6. 改完必须输出什么格式的结果

---

## 10. Handoff 制度

多个 Agent 协作最容易失控的地方，不是写代码，而是上下文交接。

因此建议强制统一 handoff 模板。

### 10.1 标准交接模板

建议每次交接至少包含以下字段：

1. 任务  
2. 目标  
3. 当前结论  
4. 已完成内容  
5. 涉及文件  
6. 未完成项  
7. 风险点  
8. 验证结果  
9. 下一步建议  
10. 禁止改动范围

### 10.2 使用原则

1. 交接必须结构化  
2. 不允许只说“你接着做”  
3. 不允许只转一堆日志而不说明结论  
4. 必须明确哪些已经确认，哪些只是推测  
5. 如果已有临时 workaround，也必须写明

### 10.3 交接目标

handoff 的目标不是把聊天记录复制给下一个 Agent，而是让下一个执行者在最短时间内知道：

1. 现在做到哪一步  
2. 还差哪一步  
3. 哪些地方不能乱动  
4. 下一步最合理的动作是什么

## 11. 状态管理制度

如果后续 Agent 增加，建议任务状态固定为一套简单状态流。

推荐状态如下：

1. `todo`  
2. `analyzing`  
3. `implementing`  
4. `reviewing`  
5. `blocked`  
6. `verified`  
7. `ready-to-merge`  
8. `done`

每个任务建议同时记录三项核心信息：

1. 当前 owner  
2. 下一处理人  
3. 当前卡点

这样做的目的不是流程化表演，而是降低多 Agent 条件下的调度混乱。

---

## 12. 冲突预防制度

多 Agent 环境中，最常见的不是语法错误，而是协作冲突。

建议固定以下硬规则：

1. 同一文件同一时段只能有一个主编辑者  
2. 同一目录进行大重构时，其他 Agent 默认只读  
3. 热修任务与重构任务不并行进入同一模块  
4. 自动生成文件由固定责任方统一处理  
5. 格式化工具与风格必须统一  
6. 合并前必须同步最新集成分支

重点防三类冲突：

### 12.1 逻辑冲突

两个 Agent 各自都改对了局部，但整体行为冲突。

### 12.2 时序冲突

一个 Agent 基于旧代码继续改，结果覆盖另一个 Agent 的新修复。

### 12.3 规范冲突

一个 Agent 只想修 bug，另一个 Agent 顺手做重构，最终 diff 失控。

制度目标不是消灭所有冲突，而是让冲突尽量在进入合并前就被发现。

---

## 13. 评审制度

不建议让每个 Agent 都“自己开发、自己评审、自己合并”。

建议至少保持以下分层：

1. 实现者负责改代码与基础验证  
2. 评审者负责指出风险与改进点  
3. 人类 Owner 负责最终是否接受与何时合并

评审关注点建议固定为：

1. 需求是否越界  
2. 改动是否过大  
3. 风格是否一致  
4. 兼容性是否考虑  
5. 测试是否足够  
6. 是否存在更小改法

如果评审发现重大问题，优先建议：

1. 退回修改  
2. 缩小范围  
3. 拆分提交

而不是直接让评审者整个接管重写。

---

## 14. 质量门禁制度

只要是 Agent 改的代码，就必须走统一质量门禁。

建议最少包含：

1. build  
2. typecheck  
3. lint  
4. 相关测试  
5. 关键路径运行验证

同时新增一条硬要求：

1. 任何 Agent 输出结果时，都必须说明“验证了什么”  
2. 不接受“理论上应该可用”作为最终交付依据

建议责任划分如下：

1. 实现者先跑与任务直接相关的基础验证  
2. 集成前由主调度或集成负责人做统一复核  
3. 人类 Owner 只看结论与风险，不负责替 Agent 补做基础验证

---

## 15. 权限制度

Agent 越多，越不应该给所有角色相同权限。

建议按三层权限控制：

### 15.1 低权限

适用对象：

1. 只做方案  
2. 只做 review  
3. 只读分析

可做事项：

1. 阅读仓库  
2. 给出建议  
3. 指出风险

不建议直接开放：

1. 高风险命令  
2. 发布  
3. 远端敏感操作

### 15.2 中权限

适用对象：

1. 主开发 Agent  
2. 专项实现 Agent

可做事项：

1. 改代码  
2. 跑本地验证  
3. 调整工程配置

不建议默认开放：

1. 直接发布  
2. 修改生产环境  
3. 处理高风险外部资源

### 15.3 高权限

适用对象：

1. 主调度兼集成 Agent  
2. 人类 Owner

可做事项：

1. 统筹集成  
2. 处理合并前最后收口  
3. 执行特定敏感操作

制度建议：

1. 开发权限可以适度分配  
2. 发布权限尽量收口  
3. 生产和密钥相关事项默认人工掌握

---

## 16. 推荐的当前落地分工

结合当前状态，推荐先采用以下模式：

### 16.1 初期模式

1. Trae：主调度 + 主开发  
2. Claude Code：方案 + review + 重构建议  
3. Codex：脚本、测试、局部模块、工具链补位  
4. 你：任务批准、优先级控制、合并与发布决策

### 16.2 为什么这样最稳

1. Trae 已有连续上下文  
2. 当前仓库主要执行链路已经在 Trae 侧沉淀  
3. Claude Code 更适合作为第二视角而不是直接抢主线  
4. Codex 更适合作为专项补充，而不是一上来承担总集成

### 16.3 何时升级到模块并行

当以下条件满足时，可以逐步升级：

1. 目录责任边界已经清楚  
2. 构建与测试命令已经稳定  
3. handoff 机制已经跑顺  
4. Agent 之间的输出格式已经统一  
5. 你能接受模块级并行带来的额外集成成本

### 16.4 当前可直接分配给 Claude Code 的首批低冲突任务

结合当前工程状态，Claude Code 现阶段更适合承担“只读分析、方案整理、文档收口”类型任务，而不直接进入高冲突主线代码区。

当前建议优先下发以下四个任务。

#### 任务一：执行端安装包边界审查

## 17. 不建议的做法

以下做法建议直接禁止：

1. 同一需求原样同时发给多个 Agent 去改代码  
2. 同一分支让多个 Agent 长时间自由写入  
3. 没有统一规则就让多个 Agent 长期进入仓库  
4. 一个 Agent 在重构时，另一个 Agent 在同目录热修  
5. 没有验证命令就让 Agent 直接交付“已完成”结论  
6. 把高风险权限默认开放给全部 Agent  
7. 把聊天记录本身当成长期项目状态系统

这些做法短期看似省事，长期一定会造成仓库失序。

## 18. 推进建议

建议把多 Agent 协作分三阶段推进。

### 第一阶段：双 Agent 稳定协作

目标：

1. 先让 Trae + Claude Code 跑通制度  
2. 建立统一规则  
3. 固化 handoff 模板  
4. 固化任务 owner 机制

### 第二阶段：三 Agent 分工试运行

目标：

1. 再把 Codex 引入专项任务  
2. 验证目录责任制是否有效  
3. 验证并行子任务是否可控

### 第三阶段：多 Agent 常态化

目标：

1. 把任务看板化  
2. 把角色制度常态化  
3. 把合并与评审制度标准化  
4. 让新增 Agent 也能按同一制度接入

推进节奏上，建议先稳，再快。

不要一开始就让多个 Agent 全面同时写代码。

---

## 19. 验收标准

这份制度真正落地后，至少应满足以下结果：

1. 新任务进入后，能明确指定 owner  
2. 多个 Agent 不会长期同时改同一文件  
3. 任务可以按分析、实现、评审三段清楚流转  
4. 人能快速知道当前谁在做什么  
5. Agent 输出结果都带验证说明  
6. 合并前能清楚知道风险点与未完成项  
7. 新 Agent 加入时，不需要重新发明整套协作方式  
8. 仓库节奏保持稳定，不因 Agent 数量增加而明显失控

## 20. 非目标

这份制度文档当前不解决以下事项：

1. 不直接规定具体工具安装步骤  
2. 不直接规定每个 Agent 的实际账号或订阅方案  
3. 不直接替代 Git 工作流文档  
4. 不直接替代 CI/CD 文档  
5. 不直接处理具体业务功能开发

它的定位很明确：

1. 先定义“多个 Agent 怎么一起工作”  
2. 再在这个制度之上推进具体研发

---

## 21. 一句话结论

后续无论是 Trae、Claude Code、Codex，还是再加入更多 Agent，都不应该按“大家一起写代码”来管理，而应该按以下方式管理：

1. 一个仓库真相源  
2. 一套统一规则  
3. 一个任务一个 owner  
4. 一个文件一个主编辑者  
5. 一个阶段一个决策人  
6. 多 Agent 在制度下分工协作

这才是后续可持续扩展的多 Agent 研发方式。
