# 测试脚本说明：应用关系与使用方式

## 1. 这套联调里到底有哪几个角色

### 1.1 手机 App

- 你手机里看到的 HelloVibe 界面，就是手机 App。
- 它负责注册、登录、查看会话、发送消息、进入设置页等。
- App 里的页面改动是否生效，取决于手机是否拿到了最新的前端 JS bundle。

### 1.2 Metro

- Metro 是 React Native / Expo 的前端调试服务。
- 它负责把最新的前端代码打包给手机 App。
- 你改了 App 文案、页面、交互后，通常需要保证 Metro 在运行，然后在手机里执行 Reload。
- 只要手机还连着当前 Metro，Reload 后就能看到新的前端代码。

### 1.3 happy-server

- `happy-server` 是本地后端服务。
- 它负责接口、WebSocket、设备状态、会话相关的后端逻辑。
- 如果 server 报错，通常要在 server 对应的终端 pane 里看日志。

### 1.4 daemon / 守护进程

- daemon 是 Mac 端常驻进程，负责让这台电脑保持“可被手机调用”的工作状态。
- 它和 `happy-server` 不是一回事。
- `happy-server` 重启，不等于 daemon 也重启。
- daemon 重启，通常也不等于手机历史会话会被清掉。

### 1.5 auth login

- `yarn cli auth login --force` 用来重新做 CLI 登录认证。
- 它适合“全新重置认证环境”场景。
- 它不是每次改前端页面、改文案、改 server 小逻辑时都要重跑的步骤。

## 2. 这几个角色之间的关系

可以把当前联调关系理解为：

- 手机 App：你实际在手机上操作的界面
- Metro：给手机 App 提供最新前端代码
- happy-server：给 App 和设备协同提供后端能力
- daemon：让 Mac 持续在线并可执行设备端能力
- auth login：在需要重建 CLI 登录身份时才使用

日常开发里最容易混淆的点是：

- 改 App 页面，主要看的是 `Metro + 手机 Reload`
- 改后端逻辑，主要看的是 `happy-server` 日志
- 想让 Mac 设备重新在线，主要看的是 daemon
- 想重建登录身份，才需要 `auth login`

所以它们不是“永远一起重启”的关系，而是按场景分别处理。

## 3. 我们刚讨论出来的关键结论

### 3.1 看前端改动时，通常不需要全链路重置

如果你只是：

- 改了设置页文案
- 改了更新日志展示
- 改了 App 页面逻辑

那通常只需要：

1. 保证 `happy-server` 正常
2. 保证 Metro 正常
3. 手机 App 执行 Reload

这时一般不需要：

- 重启 daemon
- 删除 `~/.happy`
- 重新 `auth login --force`

### 3.2 “全链路重置脚本”和“轻量三分屏脚本”不是一回事

这两类脚本要严格区分：

- 全链路重置脚本：适合环境脏了、要从头重建 server / Metro / 登录态 / daemon 链路
- 轻量三分屏脚本：适合沿用 Ghostty 三分屏流程，但不做清目录、停 daemon、强制 auth 这类重置动作

### 3.3 真正会影响登录态和设备状态的，不是普通重启，而是“重置动作”

下面这些动作要特别小心：

- 删除 `~/.happy`
- 删除 `~/.happy-rebind-20260327`
- 改 `HAPPY_HOME_DIR`
- 执行 `yarn cli auth login --force`

普通重启 `happy-server` 或普通重启 daemon，通常没有这套动作重。

### 3.4 daemon 重启后，历史会话通常还在

如果只是普通重启 daemon，而没有删除本地身份目录，也没有强制重做 auth：

- 手机里的历史会话通常还在
- 设备会短暂离线
- daemon 起来后通常会恢复在线

真正更容易改变设备绑定状态的，是“清目录 + 改 HOME_DIR + 重新 auth”的全套重置。

## 4. 当前测试脚本目录里几个脚本分别干什么

### 4.1 `20260329-全链路重启前半段一键脚本.sh`

定位：

- 普通 Terminal 版的“前半段全链路重置脚本”

它会做什么：

- 杀掉旧进程
- 停 daemon
- 删除本地登录态目录
- 启动 Docker
- 启动 `happy-server`
- 启动 Metro
- 最后进入 `yarn cli auth login --force`

适合什么时候用：

- 第一次从零搭一套联调环境
- 旧状态非常乱
- 怀疑本地身份、机器绑定、旧缓存都有污染

不适合什么时候用：

- 只是想看 App 文案改动
- 只是想原位重启 `server + Metro`
- 不想影响 daemon / 登录态

### 4.2 `20260329-全链路重启-Ghostty三分屏前半段脚本.sh`

定位：

- Ghostty 三分屏版的“前半段全链路重置脚本”

它会做什么：

- 先杀掉旧进程
- 停 daemon
- 删除本地登录态目录
- 新开一个 Ghostty 窗口
- 在新窗口里拆成三分屏
- 左侧跑 `happy-server`
- 右上跑 Metro
- 右下跑 `auth login`

适合什么时候用：

- 你就是想从零重拉一套完整链路
- 你希望把 server / Metro / auth 分开看

不适合什么时候用：

- 你已经有一套分屏在跑
- 你不想新开 Ghostty 窗口
- 你只想动 `server + Metro`

特别说明：

- 它不是“复用已有 3 分屏”
- 它是“杀旧进程后，再新建一个新的 Ghostty 三分屏窗口”

### 4.3 `20260329-daemon启动单独命令.sh`

定位：

- 单独补 daemon 的脚本

它会做什么：

- 设置 `HAPPY_SERVER_URL`
- 设置 `HAPPY_HOME_DIR`
- 启动 daemon
- 自动解析 daemon 日志路径
- 持续 tail 日志

适合什么时候用：

- `happy-server` 和 Metro 已经正常
- 登录也已经做完
- 只是缺最后一步 daemon 常驻

不适合什么时候用：

- 你还没把前面 server / Metro / auth 跑起来
- 你只是想看前端页面改动

### 4.4 `20260404-Ghostty现有分屏原位重启-server和Metro.sh`

说明：

- 文件名沿用了最初版本的命名
- 但当前实际行为已经改成“轻量三分屏启动”

定位：

- 保留 Ghostty 三分屏流程，但去掉破坏性重置动作的轻量脚本

它会做什么：

- 杀掉旧的 `happy-server dev`
- 杀掉旧的 `expo start`
- 清理相关端口：`3005`、`8081`、`9091`
- 启动 Docker 并等待可用
- 不动 daemon
- 不动登录态
- 不删除 `~/.happy`
- 不删除 `~/.happy-rebind-20260327`
- 不删除 `Machine` 表数据
- 不自动执行 `yarn cli auth login --force`
- 新开一个 Ghostty 窗口
- 在新窗口里拆成三分屏
- 左侧跑 `happy-server`
- 右上跑 Metro
- 右下给出后续操作提示

它默认提供：

- 第 1 个 pane：server
- 第 2 个 pane：Metro
- 第 3 个 pane：操作区，可按需要手动补 `auth login` 或 `daemon start`

适合什么时候用：

- 你还是想按三分屏方式拉起环境
- 你不想动 daemon / 登录态
- 你不想删除本地身份目录
- 你希望把 server / Metro / 后续操作拆开看

不适合什么时候用：

- 你就是想在当前已有 pane 里原位重启
- 你不想新开 Ghostty 窗口
- 你需要一次性做彻底重置

## 5. 这些脚本怎么选

### 5.1 日常看页面改动

优先顺序：

1. 手机 App 先直接 Reload
2. 如果 Metro / server 有问题，再用 `20260404-Ghostty现有分屏原位重启-server和Metro.sh`
3. 如非必要，不动 daemon
4. 更不要上来就跑全链路重置脚本

### 5.2 环境已经乱了，要从头重拉

优先使用：

- `20260329-全链路重启前半段一键脚本.sh`
- 或 `20260329-全链路重启-Ghostty三分屏前半段脚本.sh`

这类场景包括：

- 旧登录态不可信
- 旧 machine 绑定不可信
- 需要重新 auth
- 要从头重建联调链路

### 5.3 前面都正常，只差 daemon

优先使用：

- `20260329-daemon启动单独命令.sh`

### 5.4 你想保留三分屏流程，但不要破坏性重置

优先使用：

- `20260404-Ghostty现有分屏原位重启-server和Metro.sh`

## 6. 每个脚本执行后，你应该看到什么

### 6.1 全链路一键脚本

执行后通常会看到：

- 旧环境被清理
- 新的 server / Metro 被拉起
- 进入登录流程

### 6.2 Ghostty 三分屏全链路脚本

执行后通常会看到：

- 旧相关进程被杀掉
- 新开一个 Ghostty 窗口
- 新窗口中出现三个 pane
- 分别显示 server / Metro / auth

### 6.3 daemon 单独脚本

执行后通常会看到：

- daemon 被启动
- 当前终端开始实时显示 daemon 日志

### 6.4 轻量三分屏脚本

执行后通常会看到：

- 会新开一个 Ghostty 窗口
- 新窗口里会出现三个 pane
- 左边 pane 输出 server 日志
- 右上 pane 输出 Metro 日志
- 右下 pane 显示后续操作提示

## 7. 最后的推荐原则

以后可以直接按下面这套思路判断：

- 只看前端改动：先 Reload 手机
- Reload 不够：用轻量三分屏脚本
- 只缺 daemon：单独启动 daemon
- 整套状态乱了：再用全链路重置脚本

最重要的一条是：

- 不要把“日常开发刷新”与“全链路环境重置”混成同一件事

前者追求的是：

- 保留日志观察位置
- 保留登录态
- 快速看到改动

后者追求的是：

- 清理旧状态
- 重建链路
- 重新登录
- 统一回到一个干净起点
