# 20260401 阿里云部署更新清单

## 1. 本次目标

这次不是重做阿里云整套部署，而是基于你之前已经跑通的那一版，梳理当前版本上线时需要更新哪些部分、哪些可以不动。

---

## 2. 先按当前角色划分

当前建议仍按下面这套职责理解：

1. 阿里云服务器：
   - 承担 Web 前端
   - 承担 Happy Server
   - 承担鉴权、消息同步、控制权切换、Open in Mac 控制面
2. 本地 Mac：
   - 承担 happy-coder / daemon
   - 承担 Claude 原生终端
   - 承担 tmux 托管与实际代码执行

如果你当前线上仍是这套模式，那么本次更新重点就是：

- 阿里云更新 Server
- 阿里云更新 Web
- 本地 Mac 更新 happy-coder 并重启 daemon

---

## 3. 阿里云必须更新的部分

### 3.1 Happy Server

必须更新。

原因：

1. 本次控制权切换能力已经落到服务端路由  
2. Open in Mac handoff 逻辑增强了  
3. controller-switch 逻辑增强了  
4. `controller=mac` 时，CLI 来源消息上传放行逻辑已补齐  
5. `handoffState=switching` 的冲突与失败恢复逻辑也在服务端收口

这意味着：

- 如果阿里云上的 `happy-server` 不更新
- 但本地 Mac 的 CLI 已更新
- 新旧协议会不一致
- 很容易出现 Open in Mac、切控制权、消息同步行为异常

另外，这次还要补一个之前手册里容易遗漏的前置依赖：

- 如果生产环境 `.env.production` 里配置了 `REDIS_URL=redis://127.0.0.1:6379`
- 那阿里云机器上必须有可用的 Redis 服务
- 否则 `happy-server` 启动时会先连 Redis 并在失败时直接退出
- 线上表现就是 `pm2` 持续重启、`api.easycode-ai.xyz` 返回 502

### 3.2 Web 前端

必须更新。

原因：

1. Session 详情页里的 Open in Mac 逻辑已经增强  
2. 切换到 Mac / 切回手机的控制权入口已经补齐  
3. handoff fallback 与提示文案已经更新  
4. 当前控制方与 handoffState 的展示依赖新前端逻辑

如果阿里云上的 Web 还是旧版：

- 页面入口和后端能力会不匹配
- 用户看到的按钮、提示和真实行为容易对不上

---

## 4. 本地 Mac 必须更新的部分

### 4.1 happy-coder / daemon

必须更新。

原因：

1. Open in Mac 的 tmux-hosted 链路主要在 CLI 侧实现  
2. 本次 remote/local 切换、remote mode 恢复、消息同步修复，核心都在 CLI  
3. Mac 原生 Claude -> 手机同步恢复，也依赖新的 CLI 写入逻辑  
4. daemon 与 CLI 如果还是旧版，和新的 server/web 组合后容易出现链路半新半旧

因此本次上线时，本地 Mac 这边需要：

1. 更新 happy-coder  
2. 重启 daemon  
3. 确认 tmux 与 Claude 环境仍然正常

---

## 5. 按情况更新的部分

### 5.1 阿里云上的 happy-coder / daemon

只有在一种情况下必须更新：

- 你把阿里云机器本身也作为“可执行代码的机器”来使用

如果阿里云只是：

- Web 前端
- API Server

而不承担真实代码执行，那么阿里云机器上的 `happy-coder/daemon` 本次可以不动。

### 5.2 前端承载方式

本次不一定必须调整承载方式，但建议重新确认。

你之前的方案里有两种思路：

1. PM2 直接跑 Web/开发式前端  
2. 静态导出后由 Caddy 托管

如果当前线上已经稳定运行，可先不改承载方式；
但如果还在使用开发式前端启动方式，后续建议逐步切到：

- 静态导出 + Caddy
或
- Docker 化 Web 前端

如果你阿里云机器内存偏小，或者 `scp` / SSH 上传长期不稳定，这次 Web 更新建议直接采用你已经验证过的方式：

1. 本地 Mac 构建 `packages/happy-app/dist`
2. 把 `dist` 推到单独的 `happy-static` 仓库
3. 阿里云从 `happy-static` 拉取最新静态产物
4. 用 `rsync` 覆盖到 Caddy 的静态目录

这样可以把“前端构建”与“阿里云部署”拆开，降低服务器内存压力，也绕开 SSH 直传不稳定的问题。

按你当前阿里云机器的实际配置，Caddy 的 Web 根目录是：

- `/var/www/happy-web`

因此 Web 静态文件同步时，应该覆盖这个目录，而不是 `/var/www/happy-app`。

---

## 6. 本次大概率不用动的部分

### 6.1 数据库结构

本次提交未涉及 Prisma schema / migration 级别改动。

因此当前判断：

- 大概率不需要额外做数据库迁移

### 6.1A Redis 配置不是新功能，但必须核对

这次不是说服务端代码新增了一个 Redis 功能，而是你当前生产配置已经把 `REDIS_URL` 写进去了。

因此上线当天至少要核对两件事：

1. 阿里云本机 `127.0.0.1:6379` 是否真的有 Redis 在监听  
2. `redis-cli ping` 是否返回 `PONG`

如果没有 Redis，但又保留了 `REDIS_URL`，那就不是“可选项”，而是直接启动失败项。

### 6.2 域名与基础端口

如果你当前已经是：

- `app.xxx` 对应前端
- `api.xxx` 对应后端

且 80 / 443 / 22 已正常开放，那么这轮无需因 Open in Mac 改动而重配域名和端口。

### 6.3 Caddy 基础反向代理结构

如果你当前 Caddy 已经稳定代理：

- Web
- API

那么本次大概率不需要改 Caddy 的整体拓扑，只需要确认：

1. 前端静态目录或前端服务已更新  
2. API 反代目标仍然正确  
3. HTTPS 证书正常

---

## 7. 本次建议更新顺序

建议顺序如下：

1. 阿里云更新代码并安装依赖  
2. 阿里云更新 `happy-server`  
3. 阿里云更新 Web 前端  
4. 重启阿里云上的 server / web 相关进程  
5. 本地 Mac 更新 `happy-coder`  
6. 重启本地 daemon  
7. 做一轮手机 ↔ Mac 联调验证

---

## 8. 联调验证清单

更新完成后，建议按下面顺序验证：

1. 手机打开会话详情页  
2. 点击 Open in Mac  
3. Mac 成功进入 Claude 原生终端 / tmux 托管会话  
4. Mac 侧发消息后，手机端能同步看到  
5. 手机切回控制权时成功  
6. 切回手机后 remote mode 能恢复  
7. 手机继续发消息后，Mac 端表现正常  
8. 工具调用、目录创建、删除等动作在双端展示一致

---

## 9. 一句话结论

如果沿用你之前那套“阿里云跑 Web + Server、本地 Mac 跑 daemon + Claude”的架构，那么本次真正需要更新的是：

1. 阿里云：`happy-server`
2. 阿里云：Web 前端
3. 本地 Mac：`happy-coder` 与 daemon

而以下部分这次大概率可以不动：

1. 数据库结构
2. 域名与安全组基础配置
3. Caddy 的整体拓扑
