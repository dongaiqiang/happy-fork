# Happy Machine Key 协议对比：决策版摘要

## 1. 结论先行

当前更建议保留并继续验证“本地新协议”，暂不建议因为 upstream 当前公开实现更像旧协议，就直接回退。

原因不是“本地一定已经完全正确”，而是：

- 本地新协议的语义更清楚
- 更能解释这次 brand-new machine 仍解密失败的现象
- upstream 当前公开实现本身也带有明显历史协议包袱，不能直接当作这条链路的最终正确答案

---

## 2. 要决策的核心问题

这次不是在比较“谁更像 upstream”，而是在比较：

- 哪套协议更容易保持 App、CLI、Server 三端语义一致
- 哪套协议更能解释当前真实故障
- 哪套协议后续更容易验证和维护

---

## 3. 两套协议的本质区别

### 上游旧协议

特点：

- 关键语义依赖隐式约定
- `contentDataKey` 这个名字与实际承载含义存在混淆
- 扫码 auth 的 v2 载荷更像“只传一个 32 字节值，让 CLI 自己猜”

简单理解：

- 字段看起来像 data key
- 但实际可能被当作 public key 或 seed 的替身来使用

风险：

- App 和 CLI 稍微理解不一致，就可能出现解密失败
- brand-new machine 也可能坏，不一定只是旧数据残留

### 本地新协议

特点：

- 明确拆分 `publicKey` 与 `machineKey`
- App 回传显式结构：`version + publicKey + machineKey`
- CLI 按固定结构解析并版本化落盘

简单理解：

- 谁负责加密
- 谁负责解密
- 谁只是派生出的公钥

都说清楚了

优势：

- 更容易验证
- 更容易排障
- 更容易解释当前故障

---

## 4. 四列表

| 环节 | 上游旧协议 | 本地新协议 | 判断 |
| - | - | - | - |
| App 发什么 | 只发 33 字节，语义偏隐式 | 发 `version + publicKey + machineKey`，语义显式 | 本地新协议更清楚 |
| CLI 存什么 | 旧逻辑里 `machineKey` 关系不稳定 | 显式成对保存 `publicKey + machineKey`，并写 `dataKeyVersion: 2` | 本地新协议更可验证 |
| Server 存什么 | 原样存 `dataEncryptionKey` | 同样原样存 | Server 不是关键矛盾点 |
| App 解什么 | 用自身私钥/seed去解，但前面一旦语义错位就失败 | 同样去解，但前提材料更明确 | 本地新协议更符合真实报错现象 |

---

## 5. 为什么当前更偏向本地新协议

最关键的现象是：

- 不是只有旧 machine 解不出来
- 而是重新 auth 后，新生成的 machine 也解不出来

这说明问题更像：

- 认证回传材料有语义错位
- 或者 CLI 存盘材料关系不对
- 或者 machine 注册时使用的 key 与 App 预期不一致

而不是简单的：

- 旧数据库脏数据
- 只删几条坏记录就能解决

从这个角度看，本地新协议比上游旧协议更能解释故障。

---

## 6. 为什么不能直接以 upstream 为准

虽然 upstream 当前公开实现更像旧协议，但不能直接因此判定旧协议就是正确方向。

原因：

- upstream App 侧字段语义本身就有混淆
- upstream CLI 侧旧逻辑里还能看到 `machineKey` 处理不够稳定的历史痕迹

所以当前更合理的结论是：

- upstream 当前公开实现可以作为参考
- 但不能直接当作这条 machine key 链路的最终标准答案

---

## 7. 风险与取舍

### 方案 A：继续沿本地新协议走

优点：

- 语义清楚
- 更容易自证正确
- 更符合当前故障现象

风险：

- 与 upstream 有分叉
- 后续如果要回并，需要再做兼容设计

### 方案 B：回退到上游旧协议

优点：

- 更贴近 upstream 当前公开实现

风险：

- 可能把历史问题重新带回来
- 无法自然解释这次 brand-new machine 仍失败
- 继续保留字段语义混淆

---

## 8. 当前建议

当前建议是：

- 不要因为“upstream 现在也像旧协议”就直接回退
- 先以“显式区分 `publicKey / machineKey`”为主线继续理解和验证链路
- 后续如果验证证明这条线不成立，再考虑是否回收或兼容旧协议

一句话总结：

当前更建议把本地新协议当作主要排查和收敛方向，而不是把 upstream 旧协议当作立即回退目标。
