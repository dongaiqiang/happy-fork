# 20260331 手机端消息注入 tmux pane 专项设计说明

## 1. 问题定义

当前 `Open in Mac` 的正式方向已经拍板为：

- Mac 端使用原生 Claude 终端
- `Open in Mac` 以 tmux 为前提
- 无 tmux 时明确提示不可用

但这只解决了“**如何在 Mac 上看到原生 Claude 终端**”的问题，还没有解决另一个更关键的问题：

**当手机端继续发送消息时，如何让这条输入真正进入 tmux 中正在运行的原生 Claude 会话，而不是回退到 remote viewer。**

换句话说：

- Mac 端原生 Claude 终端已经有了承载体
- 但手机端的输入，还没有被桥接到这个承载体中

这一步如果不补齐，就会出现：

- Mac 上可以 attach 原生 Claude
- 但手机端一继续发消息，系统仍无法保持“同一原生会话 + 双端同步”

因此，“手机端消息注入 tmux pane”是后续把 **原生 Claude + 双端同步** 真正做实的关键能力。

---

## 2. 目标

本专项只解决一个非常具体的问题：

**在 controller=mobile 且会话运行于 tmux 托管环境时，把手机端发来的 user message 投递到对应 tmux pane，使 Claude 在原生终端里继续处理。**

目标效果：

1. Mac 端保持原生 Claude 终端  
2. 手机端仍可作为 controller 发消息  
3. Claude 在同一个原生 tmux 会话中继续执行  
4. Claude 输出继续通过现有同步链路回传手机端

---

## 3. 非目标

本专项明确不覆盖：

1. 无 tmux 场景下的正式双端输入支持  
2. 双端同时并发输入合并  
3. 富编辑器级别的远程编辑能力  
4. Claude 内部输入框状态的深度识别  
5. 一次性解决所有异常 pane 状态

---

## 4. 最小产品语义

为了控制复杂度，第一版产品语义必须收窄：

1. **只在 `controller=mobile` 时允许手机端注入**
2. **只在 `terminalCarrier=tmux` 且 `tmuxSessionId` 存在时允许注入**
3. **只支持“发送消息并立即提交”**
4. **不支持手机端对 Mac 原生终端做复杂编辑态接管**
5. **若注入失败，必须给用户明确错误，而不是悄悄丢失消息**

这意味着第一版不是做“远程控制终端”，而是做：

**移动端控制下，对原生 Claude 会话的安全输入投递。**

---

## 5. 目标链路

## 5.1 基本链路

理想链路如下：

1. 手机端发送一条 user message  
2. 服务端接收到该消息，判断该 session 当前：
   - controller 是否为 `mobile`
   - metadata 是否包含 `terminalCarrier='tmux'`
   - metadata 是否包含 `tmuxSessionId`
3. 若满足条件，则将这条消息路由给目标 machine / daemon  
4. daemon 根据 `tmuxSessionId` 找到目标 tmux pane  
5. daemon 使用 tmux 输入能力将消息写入 pane  
6. 必要时自动提交（Enter）  
7. Claude 在原生终端中处理该消息  
8. Claude 的后续输出继续通过现有 Happy 会话同步链路回传手机端

## 5.2 用户感知

用户感知应该是：

1. Mac 上看到的是原生 Claude 终端  
2. 手机端发消息后，Mac 上会真实看到那条输入进入 Claude 终端  
3. Claude 的回复继续同步回手机  
4. 整个过程中不切回 remote viewer

---

## 6. 核心依赖

要让这条链路成立，至少需要这些前提：

1. `session.metadata.tmuxSessionId` 已稳定存在  
2. daemon 仍在线且对应 machine 可达  
3. 对应 tmux session/window 仍存在  
4. 当前 controller 为 `mobile`  
5. 当前 Mac 端不应处于允许本地写入的 controller 状态

---

## 7. 技术方案

## 7.1 写入目标

注入的目标不是 Happy 自己的渲染层，而是：

- `tmuxSessionId` 对应的 tmux window / pane

这要求系统能从 `tmuxSessionId` 中可靠解析：

1. session 名  
2. window 名  
3. 必要时 pane 标识

## 7.2 注入动作

最小动作是：

1. 使用 tmux 的 `send-keys`
2. 将消息文本发送到目标 pane
3. 最后补一个 Enter

第一版不追求复杂度，先只支持：

1. 单次 user message
2. 自动提交
3. 成功 / 失败有明确回执

---

## 8. 必须解决的 5 个问题

## 8.1 控制权校验

如果当前 controller 不是 `mobile`，则不应允许手机端向 tmux pane 注入输入。

原因：

1. 避免手机 / Mac 双端同时写入  
2. 避免在 `controller=mac` 时手机端越权操作  
3. 保持“单 controller”语义稳定

### 规则

1. `controller=mobile`：允许注入  
2. `controller=mac`：拒绝注入  
3. `handoffState=switching`：拒绝注入

## 8.2 输入格式

单行输入最简单，但真实消息可能是多行。

第一版建议：

1. 先把消息按“普通文本输入”处理  
2. 多行情况下，按明确策略拆分并依次注入  
3. 最终统一由系统提交 Enter

后续再视需要升级为更稳健的 paste 方案。

## 8.3 自动提交

手机端“发送消息”与终端键入不是完全同一个概念。

因此第一版应明确：

1. 手机端发消息 = 系统注入文本 + 自动提交  
2. 不支持“先写不提交”的远程编辑态

## 8.4 当前 pane 状态

一个危险场景是：

1. Mac 用户在本地终端里输入到一半  
2. 手机端又发来一条消息  
3. 系统直接注入，导致输入串扰

理想的长期方案是更精细的 pane 状态识别，但第一版应通过产品约束降低风险：

1. `controller=mobile` 时，Mac 应视为观察态  
2. 观察态下不应允许本地继续写入  
3. 从而减少手机端注入与本地输入冲突

## 8.5 失败处理

注入失败时不能悄悄吞掉消息。

必须显式处理的失败包括：

1. `tmuxSessionId` 无效  
2. tmux session/window 不存在  
3. daemon 不在线  
4. controller 不允许  
5. 注入命令执行失败

### 错误返回原则

1. 手机端应看到明确失败提示  
2. 服务端应能区分“权限拒绝”“目标不存在”“执行失败”  
3. 不自动偷偷回退到 remote viewer

---

## 9. 最小实现分层

## 9.1 App

App 不负责注入本身，只负责：

1. 发 user message  
2. 感知 controller 状态  
3. 在失败时展示明确错误

## 9.2 Server

Server 负责：

1. 判断 controller 是否允许  
2. 判断 metadata 是否满足 tmux 注入前提  
3. 将注入请求路由到目标 machine  
4. 把执行结果返回给 App

## 9.3 Daemon

Daemon 负责：

1. 解析 `tmuxSessionId`  
2. 校验 tmux session/window 是否存在  
3. 执行 `send-keys`  
4. 返回成功 / 失败

---

## 10. 第一版建议边界

为了尽快落地，第一版建议边界如下：

### 支持

1. controller=mobile  
2. tmux 承载  
3. 单条消息发送  
4. 自动提交  
5. 明确报错

### 暂不支持

1. controller=mac 时的反向手机输入  
2. 双端同时写入冲突合并  
3. 高级编辑态  
4. direct 原生终端注入  
5. 智能识别 Claude 当前输入框状态

---

## 11. 风险

### 11.1 注入不等于真正理解 Claude UI

tmux 只能保证“按键送进终端”，不能天然理解 Claude 当前是不是在输入框里。

### 11.2 多行与特殊字符

消息中出现换行、引号、控制字符时，需要更谨慎处理。

### 11.3 会话漂移

如果 metadata 中 `tmuxSessionId` 失真，消息可能被投递到错误 pane。

### 11.4 观察态约束不严格

如果 Mac 在 controller=mobile 时依然可写，就会和手机端注入相互干扰。

---

## 12. 推荐实施顺序

### 第一步

先做最小 RPC：

1. `send message to tmux session`
2. 输入文本
3. 自动提交
4. 返回成功 / 失败

### 第二步

补服务端 controller 校验与错误分层。

### 第三步

补 App 端错误反馈与状态提示。

### 第四步

再考虑多行、特殊字符、pane 状态探测。

---

## 13. 结论

“手机端消息注入 tmux pane”不是附属优化，而是后续把以下三件事真正合并起来的关键桥：

1. 原生 Claude 终端  
2. 同一个会话上下文  
3. 手机 / Mac 双端同步

一句话总结：

**只有把手机端输入真正送进 tmux 中的原生 Claude 会话，`Open in Mac` 才算从“能看原生终端”走到“原生终端下也能双端协同”。**
