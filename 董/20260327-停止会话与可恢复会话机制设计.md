# 20260327 停止会话（Stop Session）与可恢复会话（Resume）机制设计

## 1. 背景与问题定义

当前产品中，“归档会话”被用户用于“暂时停一下，后续继续工作”的场景，但实现语义并不匹配：

- 从 App 侧看，详情页“归档会话”会调用 `sessionKill`（RPC 方法 `killSession`）：
  - [ops.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-app/sources/sync/ops.ts#L477-L494)
- CLI 侧收到 `killSession` 后会触发 `cleanup` 并直接退出进程：
  - [registerKillSessionHandler.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-cli/src/claude/registerKillSessionHandler.ts#L15-L29)
  - [runClaude.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-cli/src/claude/runClaude.ts#L410-L449)

这会导致一个核心问题：  
用户希望“停止并保留上下文”，但系统执行的是“立即结束进程”。在多轮对话场景下，可能出现 Claude 上下文保存不完整，恢复后“失忆”。

同时，当前 Resume 虽然已传递 `--resume <claudeSessionId>`，但它创建的是新的 Happy Session 壳，UI 历史消息与底层上下文恢复不是同一条链路。
- [run.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-cli/src/daemon/run.ts#L395-L406)

## 2. 设计目标

### 2.1 核心目标

1. 把“归档”和“停止”拆成两个明确动作：
   - **归档会话（Archive）**：语义是封存，不保证可恢复工作上下文。
   - **停止会话（Stop Session）**：语义是暂停工作，保证可继续。
2. Stop 后 Resume 必须尽可能接近命令行 `claude --resume` 的工作体验。
3. 让用户知道“当前是否可恢复”，避免黑盒行为。

### 2.2 非目标

1. 本期不做“跨两个 Happy Session 自动拼接所有历史 UI 气泡”。
2. 本期不做全量消息复制/重加密迁移（高风险、高成本）。

## 3. 现状机制复盘

当前 Session 只有 `active` 布尔语义，缺少“停止中/可恢复”这种状态：

## 3.2 终止机制（CLI）

当前 kill 走的是“快速退出”，并非“优雅停止并确认状态落盘”：
- [registerKillSessionHandler.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-cli/src/claude/registerKillSessionHandler.ts#L15-L29)
- [runClaude.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-cli/src/claude/runClaude.ts#L430-L449)

## 3.3 Resume 机制

当前 resume 参数会被传给 daemon 启动命令：

但“是否真正记住上下文”取决于停止时状态是否稳定写入。

## 4. 目标状态：会话生命周期状态机

建议把会话状态从 `active:boolean` 扩展为显式状态：

- `running`：会话运行中
- `stopping`：正在优雅停止
- `stopped`：已停止，可恢复
- `archived`：已归档，视为封存
- `failed`：停止失败或状态未知

状态迁移：

1. `running -> stopping -> stopped`
2. `running -> archived`（仅当用户明确选择归档）
3. `stopped -> running`（通过 Resume）
4. `stopping -> failed`（超时/异常）

## 5. 产品交互设计

## 5.1 详情页动作拆分

Quick Actions 改成三类动作：

1. **Stop Session（停止会话）**
   - 仅在 `running` 显示
2. **Resume Session（恢复会话）**
   - 仅在 `stopped` 显示
3. **Archive Session（归档会话）**
   - `stopped`、`failed` 可用；`running` 时二次确认风险

## 5.2 文案规范

- Stop：`将优雅停止会话并保留可恢复状态`
- Archive：`将会话封存，后续恢复不保证完整上下文`
- Resume：`从停止点继续工作`

## 5.3 可恢复性提示

在会话详情新增：
- “可恢复状态：是/否”
- “最后保存时间”
- “恢复来源 sessionId（claudeSessionId）”

## 6. 技术方案（分层）

## 6.1 App 层

新增操作：
- `sessionStopGraceful(sessionId)`（新 RPC）
- 保留 `sessionKill(sessionId)` 仅作为强制终止 fallback

现有 kill 位置：
- [ops.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-app/sources/sync/ops.ts#L477-L494)

## 6.2 Server 层

新增会话生命周期字段（建议）：
- `status: enum`
- `resumeSourceSessionId?: string`
- `resumeToken?: string`（可选）
- `stoppedAt?: Date`

保留兼容：
- `active` 可作为派生字段（`running=true` 其余 false）在过渡期同步。

## 6.3 CLI 层

新增 RPC：
- `stopSession`（优雅停止）
- `killSession`（强制终止，保留）

行为要求：
1. `stopSession` 不直接 `process.exit(0)`。
2. 先请求 Claude 主循环进入可保存状态并等待确认。
3. 等待超时后才 fallback 到 `SIGTERM` / `SIGKILL`。

## 6.4 Resume 链路

1. stopped 会话保留 `claudeSessionId`。
2. Resume 时继续走 `--resume <claudeSessionId>`。
3. 新建 Happy Session 时，在 metadata 写入：
   - `resumedFromHappySessionId`
   - `resumedFromClaudeSessionId`

这样可以为后续“跨会话聚合展示”打基础。

## 7. 兼容与迁移策略

## 7.1 历史数据兼容

旧会话默认映射规则：
- `active=true` -> `running`
- `active=false` -> `archived`（无法确认是否可恢复）

## 7.2 渐进上线

1. Phase 1：仅引入 Stop 动作 + 状态字段 + 优雅停止
2. Phase 2：补充 Resume 来源追踪字段
3. Phase 3：评估是否做 UI 跨会话连续展示

## 8. 异常与兜底策略

1. Stop 超时（比如 5~10 秒）：
   - 标记 `failed`
   - 提示用户可选择“强制终止”
2. Resume 失败：
   - 明确报错源（RPC 不可用 / sessionId 无效 / 本地状态缺失）
3. 目录不存在：
   - 维持当前二次确认创建目录流程

## 9. 验收标准

## 9.1 功能验收

1. running 会话点击 Stop 后状态变为 stopped。
2. stopped 会话点击 Resume 后，Claude 能回答“上次聊到什么”。
3. Archive 不再作为“继续工作”的推荐路径。

## 9.2 稳定性验收

1. 多轮长对话（>20 轮）Stop 后 Resume，上下文可持续。
2. 断网恢复后再次 Resume，不出现随机失忆。
3. stop 超时时有明确前端提示和 fallback 路径。

## 10. 风险与权衡

1. 优雅停止会引入等待时间，用户会感知“停会话变慢”。
2. 底层 SDK（claude-code）若无明确“保存完成回调”，仍需超时兜底。
3. 若未来要做“UI 消息完整续接”，需新增跨会话聚合查询，改造面较大。

## 11. 推荐决策

建议按以下优先级推进：

1. 先做 Stop/Archive 语义拆分（最高优先级）
2. 再做优雅停止（避免上下文丢失）
3. 最后评估 UI 跨会话连续展示（可后置）

## 12. 远期目标：异常终止后的自动恢复（Crash Recovery）

### 12.1 场景定义

用户在长会话中可能遇到非预期中断：

1. 底层进程崩溃（CLI / Claude 进程异常退出）
2. App 退后台后重进显示离线
3. 网络抖动导致实时链路断开

用户诉求：即使不是主动点击 Stop，也希望后续可以“从中断点继续工作”。

### 12.2 与本期边界

本期先交付“标准 Stop/Resume”主流程。  
Crash Recovery 作为远期目标，不阻塞本期上线。

### 12.3 远期方案要点

1. 增加崩溃状态 `crashed`
   - 状态迁移：`running -> crashed`
2. 增加恢复线索写入
   - 记录最近一次可恢复的 `claudeSessionId`
   - 记录异常退出时间、退出原因
3. 增加“尝试恢复”入口
   - crashed 会话显示 `Recover Session`
   - 优先按最近一次可恢复 sessionId 走 resume
4. 增加自动重连策略
   - App 前台恢复时自动刷新机器状态
   - daemon 重连后自动上报可恢复会话

### 12.4 验收目标（远期）

1. 非主动中断后，会话状态可见为 `crashed`（而非仅仅离线）
2. 用户可一键恢复并继续工作
3. 多轮长对话在 crash 后恢复成功率达到可接受水平

本设计文档对应用户诉求：
