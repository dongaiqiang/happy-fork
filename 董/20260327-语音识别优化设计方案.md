# 20260327-语音识别优化设计方案

## 1. 背景与目标

当前流式语音识别链路已经可用，但存在两个影响体验的核心问题：

- 问题 1：识别结果缺少断句和标点，长句可读性差。
- 问题 2：长时间讲话时，后续识别片段会覆盖前面内容，导致前文丢失。

本方案目标：

- 在不改变当前 UI 交互习惯（按钮、开始/停止、发送）的前提下，提升识别文本质量与稳定性。
- 优先做最小改动，保证可回滚、可验证、可逐步上线。

## 2. 现状分析（结合代码与历史复盘）

### 2.1 无标点的根因

后端对讯飞参数里将标点显式关闭：

- `ptt: 0`

这会导致输出文本基本无自动标点。

代码位置：

- [asrHandler.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-server/sources/app/api/socket/asrHandler.ts#L198-L206)

### 2.2 长语音覆盖前文的根因

前端当前处理 `asr_text` 的逻辑是：

- 当 `pgs === 'rpl'` 时，直接用当前片段覆盖整体文本；
- 当 `pgs !== 'rpl'` 时，追加。

这会导致动态修正阶段把此前累计文本整体替掉，表现为“后面覆盖前面”。

代码位置：

- [useStreamingAsrProvider.ts](file:///Users/dongaiqiang/Documents/mycode/codes/00-chanpin/happy-main/packages/happy-app/sources/features/voice-input/providers/useStreamingAsrProvider.ts#L170-L180)

### 2.3 与历史问题关系

历史“只能识别一个字”问题已通过以下机制修复：

- 输入按钮在 `streaming_asr` 下保持单组件，不再切组件中断监听；
- `apiSocket` 同事件改为多监听 `Set`，避免 handler 覆盖；
- 音频块统一 `audioBase64` 上送，提升 RN 兼容性。

这些修复仍然有效，不是本次覆盖问题的主因。

## 3. 优化方案（设计）

### 3.1 方案 A：标点配置化（后端）

设计思路：

- 将讯飞 `ptt` 从硬编码改为可配置；
- 默认开启标点，允许环境变量一键回退。

建议配置：

- `IFLYTEK_PTT=1`（默认）
- 需要时可临时切回 `0`

预期效果：

- 中文识别结果出现逗号、句号、问号；
- 文本可读性显著提升。

### 3.2 方案 B：双缓冲拼接状态机（前端）

设计思路：

- 不再把 `rpl` 当作“全量覆盖”；
- 改为维护两段状态：
  - `committedText`：已确认历史文本（不可被后续改写）
  - `currentSentenceText`：当前句动态修正文本（可被 `rpl` 替换）
- 输出文本统一为：`committedText + currentSentenceText`
- 当 `ls === true`（句子结束）时，把 `currentSentenceText` 归档到 `committedText`。

预期效果：

- 后续语音不会覆盖前文；
- 当前句仍保留动态纠错能力。

### 3.3 方案 C：替换范围增强（可选二期）

设计思路：

- 后端透传讯飞 `rg`（替换区间）信息；
- 前端按区间精确替换，而不是句级近似替换。

说明：

- 该方案精度更高，但改动更大；
- 建议在 A+B 稳定后作为二期增强。

## 4. 实施策略（分阶段）

### Phase 1（最小改动，优先）

- 后端：`ptt` 配置化（默认开启）
- 前端：双缓冲拼接逻辑

目标：

- 快速解决“无标点 + 覆盖前文”两大问题。

### Phase 2（增强）

- 引入 `rg` 精准替换；
- 细化断句策略与长文本可读性策略（如空格/换行规范）。

## 5. 验收标准

- 连续说 30~60 秒，前文不丢失；
- 动态修正仍可生效；
- 结果包含自然中文标点；
- 停止后文本保留，可直接发送；
- 与现有按钮交互体验一致（不引入新学习成本）。

## 6. 风险与回滚

- 风险 1：开启标点后，个别场景可能句子收口更激进。
  - 回滚：环境变量切回 `IFLYTEK_PTT=0`。
- 风险 2：拼接逻辑调整后可能出现偶发重复片段。
  - 回滚：恢复旧拼接逻辑，保留 A 方案。

## 7. 本次结论

- 本次不改代码，仅输出设计；
- 推荐先落地 Phase 1（A+B），再根据实测决定是否推进 Phase 2。
