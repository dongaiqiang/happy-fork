- **通过 probe 和真实日志，定位并修复了 tmux 底层三类关键问题**
  - 修复 1：`tmux new-window` 参数顺序错误，导致 `pane_pid` 提取失败。
  - 修复 2：`new-window -t` target 语义错误，导致把 session / window 混淆。
  - 修复 3：tmux `-e` 环境变量传参格式错误，导致 `HAPPY_HOME_DIR` 等值带上多余引号，CLI 无法读到已有认证状态。
  - 修完后，probe 已能稳定把 tmux-hosted Claude 进程拉起并保持存活，不再立刻退出。

- **定位并修复了 tmux-hosted 路径中的认证继承问题**
  - 之前 tmux 内看到的是：
    - `How would you like to authenticate?`
  - 根因不是产品逻辑要求重新认证，而是 tmux 环境变量传错，导致 Happy CLI 在 tmux 内读不到正确的 `access.key` 与登录态。
  - 修复后，独立 probe 已不再出现认证选择界面。

- **定位“为什么打开后看到的不是原生 Claude 界面”**
  - 真机与 tmux attach 观察表明：
    - 当前已经不是“打不开”
    - 而是 tmux window 里显示的仍是 Happy 的消息/摘要视图
    - 不是最终目标里的原生 Claude 终端视图
  - 通过继续排查，已把问题缩到会话恢复阶段的消息游标处理：
    - `ApiSessionClient.lastSeq` 之前从 `0` 开始
    - 恢复已有 session 时会把历史消息误当成新消息
    - 本地 launcher 因此很快退回 remote/observe UI
  - 已将 `lastSeq` 初始化为 `session.seq`，避免恢复已有 session 时从头追一遍历史消息。

- **对外部公开 upstream 又做了一轮现实校验**
  - 用 Exa 看了公开最新代码和 issue 后确认：
    - upstream 的 tmux 支持本来就更保守，主要围绕 `TMUX_SESSION_NAME` 和 remote 路径
    - 公开 issue 里也存在 tmux/detach 不稳定问题
  - 这进一步说明：
    - 我们现在做的是比公开实现更深的一条产品主路径
    - 当前问题多，主要是因为已经进入更深层的 runtime 收口阶段

## 2. 今天得到的关键结论

- **结论 1：普通新建会话与 Open in Mac hosted 必须严格分路**
  - 默认建会话不应自动走 tmux-hosted。
  - tmux / hosted 只能由 `Open in Mac` 这种显式意图触发。

- **结论 2：tmux 能否创建 window，不等于目标已经达成**
  - 早期问题已经证明：
    - window 能建出来
    - 不代表命令参数、target 语义、环境变量都正确
  - 必须用更底层日志和独立 probe 去验证实际运行状态。

- **结论 3：认证问题不是“需要重新登录”，而是“登录态上下文没继承对”**
  - 当前 tmux-hosted 路径一旦看见认证界面，说明自动拉起的环境没对齐到手工终端环境。
  - 这次根因已经确认是环境变量传参格式，而不是 Claude 本身逻辑有问题。

- **结论 4：当前 Open in Mac 已经进入“视图来源”问题，而不是“链路是否可通”问题**
  - 现在 tmux 能起、auth 能继承、Claude 进程能活。
  - 真正的问题变成：
    - Mac 端看到的是不是“同一个完整原生会话画面”
    - 还是仍然落在 Happy 自己的 remote/observe 视图

- **结论 5：tmux 里的 Happy 消息视图，证明“启动模式/恢复模式”仍未完全切到目标态**
  - 这不是“完全失败”，而是“成功打开了错误的界面类型”。
  - 也就是说，当前剩下的关键口已经从：
    - tmux 生命周期
    - auth 继承
  - 转到：
    - local / remote 模式切换
    - 会话恢复游标
    - 真正的原生终端展示语义
