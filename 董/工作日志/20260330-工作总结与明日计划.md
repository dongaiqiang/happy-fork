## 2. 今天得到的关键结论

- **结论 1：daemon 停止，不等于已有 session 立刻死亡**
  - 已有 session 仍可通过自己的 session-scoped 连接继续工作，因此“停 daemon 后还能聊天”是符合当前架构的正常现象。

- **结论 2：daemon 是远程控制入口，不是旧会话的唯一生命线**
  - 没有 daemon 时，新 session 无法从 App 端远程创建，这一点已经通过实验验证。

- **结论 3：machine online、session online、全局连接必须分开理解**
  - machine 是否还在列表里、session 是否还能聊天、设置页顶部是否显示“已连接”，不是一个状态。

- **结论 4：Open in Mac 的核心难点已经从“链路能不能通”转到“产品语义是否正确”**
  - 现在主问题已不再是 auth / decrypt / daemon 起不来，而是：
    - 会不会错误新建 session
    - 默认谁主控
    - 双端是否都能看到内容
    - Mac 看到的是不是“原生感”的界面

- **结论 5：当前自绘 remote viewer 可以工作，但很难做到原生 Claude 的观感**
  - 只要继续走“抓消息流 -> 自己重绘终端界面”这条路线，就很难完整还原 Claude 原生的 markdown、表格、tool block、滚动和交互体验。

- **结论 6：最终正确方向应是“原生 Claude 终端 + Happy 控制层”**
  - 也就是：
    - Mac 上尽量看到 Claude 自己的原生终端 UI
    - Happy 只负责会话绑定、控制权切换、双端同步与只读/可写门禁

- **结论 7：`Open in Mac` 的正式能力应当以 tmux 为前提**
  - 没有安装 tmux 时，不再勉强做 direct 原生终端的正式支持。
  - 更合理的产品语义是：
    - App 中明确提示 `Open in Mac` 当前不可用
    - 如用户只是想手动在 Mac 终端继续接该会话，可自行执行 `claude resume`

- **结论 8：没有 tmux 时，不必再硬做“两终端正式同步能力”**
  - 因为 direct 原生终端路径目前做不到完整双方同步。
  - 继续为无 tmux 场景强行补这条路，只会让产品定义和实现复杂度一起失控。
  - 所以当前更合适的策略是：
    - 正式产品能力聚焦 tmux 主路径
    - 无 tmux 时给出清晰提示与手工替代方案
