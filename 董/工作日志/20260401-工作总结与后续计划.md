# 20260401 工作总结与后续计划

## 1. 今天完成的

- **把 Open in Mac 的控制模型收口成“Mac 默认接管，手机只读观察”**
  - `Open in Mac` 成功后，控制权默认切到 Mac。
  - 手机端输入区进入只读态，避免再次出现“双端都能发消息、但审批只在终端里”的混乱状态。
  - 这次产品口径进一步明确：
    - `Open in Mac` 的目标是 **Mac 原生 Claude 终端 + tmux 托管**
    - 不是继续强化 Happy 自绘 remote viewer 作为最终形态

- **补齐了控制权切换后的服务端语义**
  - handoff 完成后，Server 侧会把 controller 正式落到 `mac`。
  - 同时保留“手机只读观察”的能力，而不是把手机彻底踢出会话同步。
  - 这样控制权和权限确认权终于开始统一到同一侧。

- **修掉了手机只读后消息完全不同步的问题根因**
  - 排查确认：
    - 问题不是 App 端只读 UI 本身
    - 而是 Server 把 `GET /messages` 也错误地卡在了 controller 门禁之后
  - 已修正为：
    - `GET /messages` 允许只读侧继续拉消息
    - `POST /messages` 仍然要求当前控制端才能发送
  - 这一步把“只读观察”和“禁止控制”真正拆开了。

- **继续修复 Open in Mac 后的重复触发与旧链路残留问题**
  - 通过日志确认，之前确实出现过同一 `happySessionId` 下旧 daemon 追踪会话和新的 tmux 托管会话并存。
  - 已在 daemon 侧加入“tmux handoff 成功后主动退休旧 tracked session”的处理。
  - 同时在 tmux-hosted local start 时清理旧的 pending permission requests，避免手机端审批的是旧请求、终端里卡的是新请求。

- **继续加强消息去重，缓解手机端同一句话出现两遍或多遍的问题**
  - App reducer 侧已经不只按 `sentFrom=cli` 去重。
  - 现在会额外识别：
    - `localId === null`
    - 文本相同
    - 时间窗口足够近
  - 用来抑制“本地已显示一次，随后又收到回声包再显示一次”的问题。

- **修掉“切回手机控制时报错、终端被异常判死”的一条关键链路**
  - 排查日志后确认：
    - 本地 launcher 已经收到了 `switch`
    - 也执行了 `doSwitch`
    - 但因为子进程随即以 `143` 退出，被后续逻辑又当成失败处理
  - 已修正为：
    - `switch` RPC 显式返回成功值
    - 如果已经进入 `switch` 退出原因，就不再把后续 `143` 当真实故障
  - 这样“切回手机失败”的老问题已经明显收敛，至少控制权切换动作本身这次已成功。

- **补了对应回归测试，覆盖本地切换场景**
  - 新增本地 launcher 测试，覆盖：
    - 收到 `switch`
    - abort 后子进程抛出 `ExitCodeError(143)`
    - 最终仍应识别为正常 `switch`
  - 保证后续继续改切换链路时，这个坑不会轻易回归。

## 2. 今天得到的关键结论

- **结论 1：切回手机后“看起来上下文没了”，不等于上下文真的丢了**
  - 你实测发现：
    - 切回手机后，Mac 终端先落到 `Remote Mode - Claude Messages`
    - 底部提示按空格切到 local mode
    - 一按空格，历史聊天记录又回来了
  - 这说明当前更像是：
    - 模式落点错了
    - 视图切到了不对的界面
  - 而不是会话上下文已被真正删除。

- **结论 2：现在至少同时存在“展示层切错模式”和“消息链路未恢复”两个问题**
  - 展示层问题：
    - 切回手机后，终端落在了错误的 remote 消息界面
  - 链路问题：
    - 手机发“你好”后没有回复
    - Mac 端也没有继续响应
  - 所以现在不是单点问题，而是切换后的恢复链路还没真正闭合。

- **结论 3：手机端不同步的问题仍未彻底解决**
  - 服务端 `GET /messages` 门禁问题虽然已修掉，
  - 但你最新实测仍然看到：
    - Mac 端正常对话
    - 手机端信息没有过来
  - 这说明除了服务端门禁外，后面至少还有一层同步/消费/游标恢复问题没处理完。

- **结论 4：Open in Mac 主目标已经达到阶段性里程碑**
  - 现在 `Open in Mac` 已经能稳定打开 **tmux 托管的 Mac 原生 Claude 终端**。
  - 这条主路径是成立的。
  - 剩下的问题，已经不再是“能不能打开”，而是：
    - 切换后是否回到正确模式
    - 双端同步是否完整
    - 手机重新接管后能否继续同一上下文

## 3. 当前停点

- **已确认可用的部分**
  - `Open in Mac` 成功
  - Mac 端原生 Claude 终端可正常对话
  - 切回手机控制这次动作本身成功，不再像之前那样直接报“未接受切换请求”

- **仍待解决的部分**
  - 手机端仍有消息不同步现象
  - 切回手机后，Mac 终端默认落在错误模式
  - 按空格切换模式后，历史聊天记录能回来，但这只是手工恢复，不是正确自动落点
  - 切回手机后，手机再发消息没有回复，Mac 端也无响应

- **当前最合理的技术判断**
  - 数据/上下文大概率还在
  - 但 controller 切换后的：
    - mode 恢复
    - consumer 恢复
    - 消息同步游标
    - 手机侧重新接管后的发送链路
  - 至少有一处还没有真正切回稳定状态

## 4. 后续计划

- **优先查“切回手机后为什么默认落到 Remote Mode 界面”**
  - 重点看：
    - `switch -> remote` 后本地 launcher 与 UI 模式如何收口
    - 为什么终端默认停在 `Remote Mode - Claude Messages`
    - 为什么需要手工按空格，历史会话才重新出现

- **继续查“切回手机后，消息为什么没人处理”**
  - 重点看：
    - 手机端发送后是否真正进入 server / sync 队列
    - remote consumer 是否重新接管成功
    - 切换后是否错误地停在某个“等待新 Claude session”的过渡态

- **继续查“Mac 对话内容为什么还不同步到手机”**
  - 既然 `GET /messages` 门禁已修掉，下一步应重点排：
    - 服务端是否正确产出消息
    - App 侧是否真正消费到新消息
    - 是否还存在 seq / cursor / 去重误杀 / envelope 过滤问题

- **把“切换后模式错位”和“同步链路断开”合并成同一条恢复链路问题来处理**
  - 不再拆成互不相关的小问题分别修。
  - 因为从现象上看，它们很可能都发生在：
    - Mac local -> mobile remote 接管
    - 会话恢复 / 模式恢复 / 消费者恢复
  - 这一条链路的同一个阶段。

- **在主链稳定后，再进入阿里云部署验证**
  - 明天形成阶段性版本的方向不变。
  - 但优先级上，仍应先保证：
    - Open in Mac 打开正确
    - 手机同步正常
    - 控制权来回切换后还能继续同一会话
  - 这三点稳定后，再推进阿里云部署会更稳。
