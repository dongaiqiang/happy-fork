# Happy 项目原生架构设计与生产级部署指南

本指南详细解析了 Happy 项目的原始云原生架构设计理念，并提供了如何在生产环境（或高要求的局域网环境）中进行标准的、不踩坑的部署方案。

---

## 1. 核心架构设计解析

Happy 的架构是为了**“纯粹的云端分离”**与**“极致的隐私安全”**而设计的。理解了这三个核心角色，就能明白其对网络和证书的严苛要求。

### 角色 A：Server (云端信令中心 / 邮局)
- **定位**：部署在公网的中心服务器。
- **职责**：它**不存储**任何业务明文数据，也**不执行**任何 AI 逻辑或代码。它仅仅负责用户身份鉴权、设备在线状态维护，以及在 Web 端和 Daemon 端之间进行**加密消息的路由转发**（类似于一个只负责传信的邮局）。
- **要求**：必须拥有合法的公网域名和受信任的 HTTPS (WSS) 证书。

### 角色 B：Web UI (前端控制台)
- **定位**：运行在浏览器（手机、平板、电脑）中的纯前端 SPA 应用。
- **职责**：负责 UI 展示与用户交互。
- **安全机制（核心卡点）**：为了保证云端 Server 无法偷窥用户的对话，Web 端强制使用浏览器的 `Web Crypto API` 进行**端到端加密（E2E）**。所有的消息在离开浏览器前都已经被加密。
- **要求**：浏览器严格规定，`Web Crypto API` 只有在 **Secure Context（安全上下文，即 `localhost` 或合法的 `HTTPS`）** 下才可用。这也是为什么用普通的局域网 IP (`http://172.20.x.x`) 访问时功能会直接瘫痪。

### 角色 C：Daemon / CLI (本地计算节点 / 真实打工人)
- **定位**：运行在你自己的电脑或云端开发机上的后台 Node.js 进程。
- **职责**：它拥有解密私钥。当它通过 WSS（WebSocket Secure）长连接到 Server 时，它会接收加密指令、解密、执行代码/调用 AI 模型，然后将结果加密发回 Server。
- **要求**：作为底层的 Node.js 客户端，它在发起 WSS 连接时会**严格校验 Server 证书的合法性**。如果 Server 用的是自签名证书（未受信任的 CA），Daemon 会直接报 `TransportError` 并拒绝连接。

---

## 2. 为什么在本地局域网（无域名）部署会极其痛苦？

在纯本地（如 `172.20.x.x`）部署时，我们相当于把一套“需要广域网公信力”的架构强行塞进了一个内网。
这会导致**信任链断裂**：

1. 手机访问 HTTP IP -> 浏览器因为不安全，禁用加密 API。
2. 手机访问自签名 HTTPS IP -> 浏览器拦截，需手动点“继续访问”，且后台的 API 请求可能因跨域/证书问题被静默拦截。
3. Daemon 访问自签名 HTTPS IP -> Node.js 底层直接判定证书非法，切断 WebSocket。

我们在本地测试时使用的“绕路方案”（Web走自签名HTTPS代理，Daemon走本机HTTP），只是一种用于快速开发的 Hack 手段。

## 3. 生产级/正规军部署方案 (The Right Way)

如果你希望在家庭局域网、公司内网，或者公网上真正稳定、优雅地部署 Happy，且支持手机无缝访问，**必须走标准的域名 + 真实证书路线**。

### 前置准备
1. **一个真实的域名**：如 `myhappy.com`（在阿里云、腾讯云或 Cloudflare 购买）。
2. **一台永远开机的宿主机**：如你的 Mac Mini、NAS 或一台云服务器。

### 部署步骤

#### Step 1: 配置域名解析
- **云端部署**：将 `*.myhappy.com` 解析到你的公网服务器 IP。
- **纯局域网部署（进阶）**：在你的路由器（或 OpenWrt 软路由、AdGuard Home、Pi-hole）中配置 **DNS 劫持/自定义解析**，将 `app.myhappy.com` 和 `api.myhappy.com` 指向你跑服务的电脑的局域网 IP（如 `172.20.10.2`）。

#### Step 2: 使用 Caddy 或 Nginx 自动申请真实证书
推荐使用 `Caddy`，因为它内置了 Let's Encrypt 的自动证书申请功能。

编写一个 `Caddyfile`：
```caddyfile
# Web 前端代理
app.myhappy.com {
    reverse_proxy localhost:8083
}

# Server 后端/WebSocket 代理
api.myhappy.com {
    reverse_proxy localhost:3005
}
```
*注：如果是局域网部署，由于 Caddy 无法通过外网 HTTP 验证，你需要配置 Caddy 的 DNS 验证插件（如 Cloudflare DNS API），让 Caddy 通过 DNS 记录向 Let's Encrypt 证明你拥有该域名，从而颁发合法的真实证书给局域网机器。*

#### Step 3: 启动底层服务
在宿主机上正常启动 HTTP 服务：
```bash
# 启动 Server
METRICS_ENABLED=false bash ./01-start-server.sh

# 启动 Web
bash ./02-start-web.sh
```

#### Step 4: 连接与使用
此时，整个架构已经达到了生产级标准。

1. **配置 Web**：手机浏览器打开 `https://app.myhappy.com`（此时会有绿色的安全小锁，没有任何拦截）。在设置中将 Server URL 设为 `https://api.myhappy.com`。
2. **登录 Daemon**：在宿主机终端执行：
   ```bash
   HAPPY_SERVER_URL=https://api.myhappy.com yarn workspace happy-coder cli auth login
   ```
3. **启动 Daemon**：
   ```bash
   HAPPY_SERVER_URL=https://api.myhappy.com yarn workspace happy-coder cli daemon start-sync
   ```

### 为什么这是完美的？
- **手机浏览器**看到的是由权威机构签发的真实证书，完全满足 Secure Context，`Web Crypto API` 满血运行，没有任何弹窗警告。
- **Daemon 进程**在连接 `wss://api.myhappy.com` 时，Node.js 底层校验发现证书合法，WebSocket 长连接瞬间建立，永不断线。
- 整个流程符合 Happy 团队设计这套 E2E 加密架构的初衷。
