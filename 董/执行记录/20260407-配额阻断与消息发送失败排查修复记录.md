## 3. 真实根因定位

### 3.1 服务端门禁链路结论

- `/Users/dongaiqiang/Documents/mycode/codes/00-chanpin/hellovibe-main/packages/happy-server/sources/app/api/routes/v3SessionRoutes.ts`
  在消息入库前先执行 `checkSubscriptionValidity(userId)`，再执行 `getUserQuota(userId)` 的日/月额度判断
- `/Users/dongaiqiang/Documents/mycode/codes/00-chanpin/hellovibe-main/packages/happy-server/sources/app/api/middleware/tokenQuota.ts`
  对 quota / validity 命中时统一返回 `429 + error + reason + message + upgradeUrl`
- 如果真实命中：
  - 试用到期：`429 / validity_check_failed / trial_expired`
  - 订阅 inactive：`429 / validity_check_failed / subscription_inactive`
  - 订阅过期：`429 / validity_check_failed / subscription_expired`
  - 日额度不足：`429 / quota_limit_exceeded / daily_limit_exceeded`
  - 月额度不足：`429 / quota_limit_exceeded / monthly_limit_exceeded`
- 同一条消息链路里，若 session 当前不是 mobile controller，服务端会返回：
  - `409 / mobile-controller-required`
  - 或 `409 / switching-in-progress`

### 3.2 前端发送链路结论

- `/Users/dongaiqiang/Documents/mycode/codes/00-chanpin/hellovibe-main/packages/happy-app/sources/sync/sync.ts`
  的 `handleBackgroundSendTimeout()` 会在 pending outbox 持续 30 秒未清空时插入用户侧可见提示：
  - `Message failed to send in background after 30s. Please retry.`
- 这条提示不是服务端返回值，而是前端 background watchdog 自己生成的超时文案
- `/Users/dongaiqiang/Documents/mycode/codes/00-chanpin/hellovibe-main/packages/happy-app/sources/sync/messageSendFailure.ts`
  修复前只把 `429 quota_limit_exceeded` 和 `429 validity_check_failed` 认定为不可重试
- 修复前对 `409 mobile-controller-required` 和 `409 switching-in-progress` 误判为可重试错误
- 结果是：
  1. 服务端已经明确返回 409
  2. 前端没有停止 retry，也没有把控制权冲突转成可理解提示
  3. pending outbox 一直留在队列中
  4. 一旦 App 处于 background / inactive 超过 30 秒，就会被 watchdog 改写成笼统超时提示

### 3.3 结论

- 本次用户看到的表象是：`Message failed to send in background after 30s. Please retry.`
- 本次真实根因不是“quota 命中后前端完全不认识”，因为 429 quota / validity 早已被前端识别为不可重试
- 本次更符合的真实根因是：
  - 会话控制权已不在 mobile，或仍在 handoff 切换中
  - 前端把 `409 mobile-controller-required / switching-in-progress` 误当作可重试异常
  - 后续被 background timeout watchdog 覆盖为 30 秒超时提示
- 因此本次属于：
  - `前端错误处理不准确`
  - `消息发送 background timeout 表象`
  - `控制权冲突导致的实际阻断`
  - 不是本次主要根因的 quota / validity 门禁
